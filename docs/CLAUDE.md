# makoto2 開発ガイド

このファイルがプロジェクトのルール・構造・履歴の**正本**。メモリ（`MEMORY.md`）はポインタと補足だけを持つ。

## プロジェクト概要

**MAKOTO** は、剣崎真琴（キュアソード / CV: 宮本佳那子）をモデルにした AI マスコットボット。Mastodon サーバー「キュアスタ！」（precure.ml）で稼働する。

- **アカウントは継続使用**: [@makoto](https://precure.ml/@makoto)（44,161 投稿・最終投稿 2026-06-24）
- **コードは作り直し**: 旧実装 [pooza/makoto](https://github.com/pooza/makoto)（最終コミット 2024-11-10）はアーカイブ済み。**使い回さない**
- **言語・スタックは自由**（Ruby 縛りなし）。未決＝下記「未決事項」
- **稼働先は旧サーバー（lbock）非依存**。専用 CT（2GB）に隔離して建てる。旧実装は本番サーバー（lbock）に同居して孤児プロセスを撒いた前科があるため、同居させない。**開発用 CT (`bydo`) は 2026-07-30 に用意済み。本番も pve 内にもう 1 CT 建てる**（→ 下記「実行環境」）
- **入出力は非対称にする**（旧 makoto と同じ）。**出す側は抽象化し、読む側は Mastodon に決め打つ** → 下記「入出力の非対称性」

**ハドラーブロス**（[@hadlarbot](https://mstdn.delmulin.com/@hadlarbot)・895 投稿・最終 2025-01-06）は **makoto2 のスコープ外**。要件が MAKOTO とまったく異なり、**必要なのはチャットボットの部分だけで、急いでもいない**。同じリポジトリに同居させると、絞り込んだ 4 機能に無関係な分岐を抱え込むだけになる。**復活させるときは別リポジトリで別立てにする。**

## 設計方針

### キャラの一貫性を第一の評価軸にする

旧実装は台詞コーパスを**そのまま返していた**とみられ、文脈を無視した投稿が実際に出ていた。これが「キャラのぶれ」の正体である可能性が高い。作り直しでは**コーパスを LLM の few-shot / RAG 素材として使う**方式に変える（詳細と実データは [makoto-legacy.md](makoto-legacy.md)）。

⚠ **語り口だけを見ても足りない。****本編に無いことを語っていないか**も評価軸に入れる。真琴は孤児だが**出自を語る台詞がコーパスに 1 件も無い**ので、LLM に任せると設定を創作する。人物設定と「語ってよい範囲」は [makoto-persona.md](makoto-persona.md) を正本にする（宮本佳那子さんのパーソナリティが混じって扱われてきた理由もそこ）。

### SNS 本体を改造しない

モロヘイヤの設計方針をそのまま継承する。MAKOTO も **Mastodon 本体（フォーク含む）に手を入れずに、公開 API と webhook の外側で完結させる**。本体パッチが増えるほど upstream 追従の工数と衝突リスクが膨らむ。

### プリキュアの情報は cure-api から REST で取る（2026-07-30 決定）

⚠ **rubicure を直接使わない。** シリーズ一覧のようなプリキュアの基礎情報は、[cure-api](https://github.com/pooza/cure-api) の REST エンドポイントから取得する。

- **経緯**: rubicure は上流が **Ruby での実装そのもの**に軸足を置いており、**作品のデータを充実させる**方向とは関心が異なる。cure-api はその受け皿として作られたもので、**MAKOTO が必要とするのは後者**。参照すべき正本は gem ではなく cure-api の側にある
- **したがって、作品の情報が足りないときは MAKOTO 側に抱え込まず、cure-api を伸ばす。** シリーズ名や放送年をこのリポジトリにハードコードし始めたら、正本が 2 つに割れた合図
- 実務上も、ライブラリを抱え込むと同じデータの写しがもう 1 つ増え、更新のたびに MAKOTO 側の再デプロイが要る。cure-api は既に公開されていて（`https://cure-api.precure.ml`）、キュアスタ！でも使っている
- ⚠ **cure-api に載せるのはプリキュアの情報だけ**（2026-08-08 整理）。cure-api は元々**プリキュア淑女録スプレッドシートにアクセスする API デーモン**なので、⚠ **スプレッドシートで管理したいプリキュアのデータ（旧実装が持っていた妖精など）は cure-api を伸ばす**。⚠ **MAKOTO が Google Sheets API を直接叩く形にはしない**（サービスアカウントを持つ箱を増やさない）
- ⚠⚠ **MAKOTO の原稿は cure-api に載せない。**原稿はプリキュアの情報ではなく、載せると cure-api の役割が「プリキュアの情報を返す API」から外れる。**必要になったら別の方法を考える**（→ #50）
- ⚠⚠ **cure-api に認証を足す前提の設計をしない**（2026-08-08 方針）。cure-api は**認証を持たない公開 API**として運用する。⚠ **したがって「認証を掛ければ非公開データも置ける」という逃げ道は無い。****非公開のものは cure-api の外に置く**（未公開の台本がその代表例）

| エンドポイント | 返るもの |
| --- | --- |
| `GET /series` | `[{"key": "dokidoki", "title": "ドキドキ！プリキュア"}, ...]`（2026-07-30 時点で 24 件） |
| `GET /series/index` | `key` の配列だけ |
| `GET /series/:key` | そのシリーズの詳細 |
| `GET /singers` | プリキュア歌手の名義（`name` ＋ グループの `members`。2026-08-13 時点で 50 名義）。⚠ **ライブのゲストコーナーが母集合を絞るのに使う**（→ 下記「ライブの並びは抽選ではなく整列」） |

⚠ **名義の表記揺れは MAKOTO 側で吸収する**（`CureApiService.normalize`＝NFKC ＋ 空白除去。cure-api の `Datasource.normalize_name` と同じ規則）。⚠⚠ **スプレッドシートは「宮本 佳那子」、iTunes 由来の曲データは「宮本佳那子」。**ここが噛み合わないと 1 件も一致しない。

収集スクリプト（[seed/](../seed/)）も同じ方針に揃える。**ローカルの作業コピーのパスを埋め込まない**（`/home/pooza/repos/rubicure/...` のような書き方は、他の端末で動かない）。

### 入出力の非対称性: 出す側は抽象化、読む側は Mastodon 決め打ち（2026-07-31 整理）

**旧 makoto と同じ仕様。**投稿と受信で扱いを変える。

| 向き | 経路 | 抽象化するか |
| --- | --- | --- |
| **出す**（投稿） | モロヘイヤの **Slack 互換 webhook**（`POST /mulukhiya/webhook/{digest}`）／ Mastodon API 直 | **する。**Slack 互換 webhook を実装した他サービスにも同じコードで向けられる |
| **読む**（メンション検知） | Mastodon の **Streaming API**（WebSocket） | **しない。Mastodon に決め打つ。**読む側は SNS 固有の仕様に踏み込むので、抽象化しても得るものが無い |

⚠ **どちらも outbound。**「inbound は開けない」（→ 下記「実行環境」）と矛盾しない。webhook は**送りつける側**であって、MAKOTO が受け口を持つのではない。Streaming API も MAKOTO 側から張る WebSocket 接続。

⚠ **「モロヘイヤの webhook を受ける」という書き方をしない。**向きが逆に読めて、inbound を開ける話だと誤解される（実際に一度誤読された）。

#### ✅ 画像添付は実装しない。URL を貼って SNS のプレビューカードに任せる

**曲紹介のアートワークは、URL を貼れば Mastodon 側が OGP のプレビューカードとして補完する**（→ [track-corpus.md](track-corpus.md)）。⚠ **これは SNS 側の機能なので、出力先を抽象化しても失われない。**

⚠ **モロヘイヤ経由の場合は `ItunesImageHandler` が画像も添付するため二重になりうる**（`handle_pre_webhook` は `handle_pre_toot` に委譲するので webhook 経由でも走る）。**#16 で実機確認し、必要ならモロヘイヤ側で切る。**

#### ⚠ ストリーミング受信は「里帰り」になる

**モロヘイヤの `Listener`（`app/lib/mulukhiya/listener.rb`）は旧 makoto から移植された実装。**makoto2 で書くと、出ていったものが戻ってくる形になる。

- **参照するのは旧 makoto ではなくモロヘイヤ版。**移植後にモロヘイヤ側で手が入っており（指数バックオフ・シグナル処理・最終受信時刻のハートビート）、本番で揉まれている。旧実装はアーカイブ済みで、そちらを掘る理由が無い
- **「コードは作り直し・旧実装は使い回さない」とは矛盾しない。**スタックの決定で「フレームワークは引き継ぐ」としたのと同じ扱いで、**キャラの一貫性に関わらない配管**だから。逆に、台詞の使い方（そのまま返す）は引き継がない
- ⚠ **モロヘイヤ版をそのまま持ってこられない。**`EventMachine` のイベントループと最終受信時刻の Redis 保存を前提にしており、MAKOTO は**常駐 1 本＋内蔵スケジューラ・Redis 無し**。同居のさせ方は設計時に決める

### 管理操作は CLI で行う（WebUI の管理コンソールは作らない）

旧実装は `/makoto` に管理コンソールを持っていたが、**パスを知る利用者は運用者ひとりだった**うえ、退役後も nginx に残骸を残した（→ [makoto-legacy.md](makoto-legacy.md)）。makoto2 では管理コンソールを作らず、**原稿・辞書・曲データの更新といった運用操作はコマンドラインのサブコマンドとして実装する**。

- 認証・セッション・画面という付随物を持ち込まずに済む
- SSH 越しに実行でき、デプロイ・監視と同じ経路に乗る
- 旧実装で Issue が立っていた「WebUI からの辞書更新」も、**WebUI ではなく CLI として作る**

なお「WebUI」は利用者向けの機能を指す語としては引き続き使う（表記規約）。ここで作らないと決めたのは**運用者向けの管理コンソール**。

#### ✅ 原稿の登録も CLI のままでよい（2026-08-14 判断）

**旧実装はスプレッドシートで原稿を編集していた**（レイアウトは `message` テーブルと完全に一致。`type` / `feature` / `month` / `day` / `message` / `data`）。⚠ **PostgreSQL だったので、手元の GUI からサーバーのデータに繋げた。**SQLite は原理的にそれを持てない。

⚠⚠ **しかし「本番の DB を GUI で触る」は、この設計と正面衝突する** — 管理コンソールを作らない / inbound は開けない / **稼働中の SQLite を生でコピーしない**。

**そのうえで、CLI のままでよいと判断した。手で書く頻度が低いため。**

| | 頻度 | 手段 |
| --- | --- | --- |
| **特定日の原稿**（元日・バレンタイン・エイプリルフールのおふざけ等） | ⚠ **年 6 回程度** | **手で書く。**CLI ＋ ファイル取り込み（#50）で足りる |
| **`morning`（他愛もない日常話）** | ⚠⚠ **飽きられない量が要る** | **生成で埋める**（→ #17。⚠ **事前生成なので人が読んで落とせる**） |

⚠ **「登録が大変」と感じていたのは後者だけ。**⚠⚠ **そちらは登録の道具ではなく、生成と選別の問題**なので、GUI もスプレッドシートも要らない。

##### ✅ 台本の置き場は [pooza/makoto-scripts](https://github.com/pooza/makoto-scripts)（private・2026-08-15・#50）

⚠⚠ **`var/script/` に置いていた台本を移した。**⚠ **`var/` は gitignore 対象で、この端末にしか無かった** — **原稿は `message` テーブルの行で DB も git 管理下に無い**ので、⚠⚠ **`bydo` に入れた台本が本番へ運ばれない。**

- ⚠ **makoto2 は public なので、投稿前の台本をこちらにコミットもできない**（ネタバレ防止）。**だから private リポジトリに分けた**
- ⚠ **private にした理由は「秘密だから」ではない。**⚠⚠ **したがって資格情報や鍵はあちらにも置かない**（cure-api で決めた「認証を掛ければ非公開データも置ける、という逃げ道は無い」と同じ考え方）
- **取り込みは `bin/makoto message import ~/repos/makoto-scripts --prune`。**⚠ **何度流してもよい**（`slug` で upsert）。⚠⚠ **`--prune` は `slug` を持つ行しか消さない**ので、`makoto message add` で足した原稿と旧ダンプ 388 件には触らない
- ⚠⚠ **本番用の台本は必ずあちらを正本にする。**⚠ **`var/script/` に複製を残さない**（当日どちらが入っているか分からなくなる）。リハーサル用の使い捨ては置いてよい
- ⚠⚠ **`makoto message add` で足した原稿は `--prune` で消えない**（`slug` を持つ行しか消さないため）。⚠ **取り込みで足した版と二重になり、`MessageSelector` がどちらかを乱択する**
  - ⚠ **2026-08-15 に実際に踏んだ** — 予告 3 本が `bydo` の DB に `slug` 無しで存在し、正本から取り込んだ 3 本と合わせて**同じ日に 2 本**になった。**手で消すしかない**（`makoto message remove ID`）
  - ⚠⚠ **原稿は DB の行なので、ホストごとに中身が違う。**⚠ **「手元に無い＝どこにも無い」ではない。**逆に**「`bydo` にある＝本番にもある」でもない**（この 3 本は本番には無かった）。**確認するときは必ず対象のホストで見る**
- ⚠ **語りの register が 3 つある**ことを、あちらの README に書いた — **自分について＝寡黙 / ファンに向けて＝言葉が増える / ⚠⚠ 他の歌手について＝敬意を向ける（敬語）**

### コミュニティ・文化に資する

モロヘイヤと同じ北極星を共有する。MAKOTO は「サーバーを便利にするユーティリティ」ではなく、**コミュニティの文化そのものを増幅する存在**として設計する。増幅であって制度化ではない（参加は任意を死守する）。

### プロセスの寿命を設計に含める

旧実装は 2026-06 に**孤児プロセスが 11 日分たまり swap を 800MB 占有**し、同居していた本番サーバーの投稿レイテンシを劣化させた。停止・再起動・死活監視を後付けにせず最初から設計に含める。

⚠ **monit の `exec` は argv に分割されるため `&&` 以降が黙って捨てられる。** 本番 3 台の自動復旧がこれで長期間死んでいた実例がある。復旧コマンドはラッパースクリプトに逃がす。

### 死活監視は「生きているか」と「仕事をしているか」を分ける（2026-08-08 決定・#15）

⚠⚠ **systemd の `Restart=always` はプロセスの死しか見ない。**⚠ 実際に **2026-08-05 から 08 までの 3 日間、常駐は生きたまま `jobs: 0`（投稿の登録が 0 本）だった。**プロセスの生死だけを見る監視ではこれを検知できない。

- **監視の口は `makoto status`**（`Makoto::Health`）。⚠ **終了コードで返す** — **`0` 健全 / `1` 異常（復旧させる）/ `2` 警告（人が見る）**
- 見るのは 5 つ。**生死** / ⚠ **登録された投稿の数**（0 は異常）/ ⚠ **ハートビートからの経過**（止まっていればスケジューラが死んでいる）/ ⚠⚠ **連続して落ちた投稿の本数**（警告）/ **孤児プロセス**
- ⚠⚠ **「登録された本数」は「出た本数」ではない**（2026-08-15・#78）。`jobs` は**起動時に決まる定数**なので、⚠ **トークンが失効しても `source` が毎回落ちても、`jobs: 5` のまま exit 0 を返し続けた** — **160 枠が全滅しても健全に見える形**だった
  - ⚠⚠ **枠の結末を 3 つに分けて、失敗の側だけを数える**（`Heartbeat`）。**投稿できた**（数を 0 に戻す）／⚠ **本文が無い**（**何も記録しない**）／⚠ **`source` が落ちた・投稿が失敗した**（1 つ進める）
  - 🔴 **「本文が無い」を中立に置くのが肝。**⚠ **これを失敗に数えると、原稿がまだ無いだけの日が延々と警告になる**（MAKOTO は 8/15〜10/31 の 2 か月半がこれ）。⚠⚠ **逆に成功に数えると、#77 の「設定を消すと枠の中で例外が上がる」形が中立に紛れる**（その経路も本文が nil になる）。**だから `source` の失敗と空の本文を `PostingJob` の側で分けている**
  - ⚠⚠ **これは「異常（1）」ではなく「警告（2）」。**⚠ **再起動で直らないから** — 原因は**トークンの失効・設定の欠落・`source` の不具合・Mastodon 側の障害**で、どれも常駐を入れ直しても変わらない。**孤児で復旧を叩かせないのと同じ形**（#78 の起票は `errors` に置く案だったが、この理由で変えた）
  - ⚠ **この警告は時間で消えない。消えるのは「次に 1 本投稿できたとき」だけ。**⚠⚠ **時間で消える形にすると、投稿していない期間＝検証されていない期間に、警告のほうが先に消える**
  - ⚠⚠ **同じ枠を 2 度数えない**（冪等キーで畳む）。⚠ **`Scheduler` は登録直後に初回 tick を叩いてから `every` で回す**ので、**拾う幅（既定 10 秒）の内側で同じ枠が 2 回来る。再起動が挟まれば毎回そうなる。**⚠⚠ **成功は Mastodon 側が冪等キーで畳むのに失敗だけ畳まれず、落ちた枠 1 つで閾値を 2 つ消費していた**（2026-08-15・#81 のレビュー指摘・実測）。**「投稿の側で冪等にしたものは、観測の側でも冪等にする」**
- ⚠ **ハートビートの痕跡は `tmp/run/heartbeat.json`**（`Makoto::Heartbeat`）。⚠ **監視にログを読ませない**（置き場と書式に依存させない）。⚠ **観測用の痕跡であって進行位置の状態ではない**ので、消しても再起動後の動作は変わらない
  - 🔴 **痕跡は「切り詰めて書く」のではなく「差し替える」**（2026-08-15・#81 のレビュー指摘）。⚠⚠ **`File.write` は切り詰めてから書くので、その隙に読んだ側は壊れた JSON を掴む。**⚠ **読めない痕跡は `stale?` が true になる**ので、**`makoto status` が 1 を返し、monit が正常な常駐を再起動する** — **監視のせいで監視が誤報する形**だった。⚠ **実測で 2,000 回中 625 回が nil**（#78 で投稿ごとに書くようになり、1 時間に 1 回 → ライブ当日 160 回と窓が広がった）。**同じディレクトリ内の rename は不可分なので、読む側は鍵を取らなくてよい**
  - ⚠⚠ **更新は `flock` でプロセスもまたいで直列化する。**⚠ **`Mutex` はプロセス内のスレッドしか守らない**が、**常駐は再起動で一時的に 2 本になりうる**（孤児で復旧を叩かせない理由と同じ前提）。⚠ **実測で 600 回の更新のうち 458 回が消えた**
- ⚠⚠ **止まったとみなす閾値は設定から出す**（`/scheduler/heartbeat/interval` の 3 倍、投稿の失敗は `/scheduler/posting/failure_limit`）。**間隔を延ばした瞬間に監視が誤検知しはじめる**のを防ぐ。⚠ **どちらも既定値に逃がさない**（`optional_config` を使わない）— **設定を消しただけで検知が静かに緩む形にしない**（#77 の裏返し。schema で必須にしてあるので `rake config:lint` が先に止める）
- ⚠⚠ **孤児プロセスは警告どまりで、復旧を叩かせない。**再起動の瞬間に一時的に 2 本になりうるので、ここで再起動させると**検知 → 再起動 → 検知のループ**になる。⚠ **孤児は「溜まる」のが問題**（旧実装は 11 日分溜めた）なので、即時の自動復旧より人の目が要る
- ⚠ **`/proc` が読めない環境では「孤児は無い」と答えない**（不明を返す）。**守っているつもりで無防備**になるのを防ぐ
- ⚠⚠ **孤児かどうかは cmdline の部分一致で決めない**（2026-08-15・#61）。⚠ **argv にこの文字列を含むだけの無関係なプロセスを孤児と報告する** — 踏みやすいのは**復旧のラッパースクリプト・デプロイのシェル・`pgrep` のワンライナー**で、⚠ **docs が「復旧コマンドはラッパースクリプトに逃がす」と決めている以上、この形は運用に組み込まれる。**⚠ **恒常的に踏むと本物の孤児が誤報に埋もれる**
  - **見るのは 2 つだけ**（`Health#script_candidates`）— ⚠ **argv の 0 番目**と、⚠⚠ **インタプリタのオプションを読み飛ばした次の 1 つ**。**位置で決め打つと `ruby --yjit bin/makoto_daemon.rb start` を取り逃がす**（#68 のレビュー指摘。⚠ **bydo の Ruby は YJIT 有効**なので実際に取りうる形）。⚠ **オプションでない要素は 1 つ目で打ち切る** — `bash -lc 'bundle exec bin/makoto_daemon.rb restart'` の第 3 要素は**スクリプトではなくシェルへの文字列**で、そこまで見ると部分一致に戻る
  - ⚠⚠ **ただし要素をそのまま突き合わせると本物を取り逃がす。**⚠ **実機の常駐は argv が `bin/makoto_daemon.rb start` という 1 要素**（bundler 経由の起動で `$0` が書き換わる。2026-08-15 に bydo の `/proc/{pid}/cmdline` を実測）。**要素の中を空白で割ってから basename を見る**
  - ⚠ **「誤報を出さない」と「本物を検知する」の両方を回帰テストに入れる**（#61 の完了条件）。**片方だけでは通ってしまう** — 実際、旧実装は前者だけ落ちる

### 投稿の欠落は詰めない。進行位置は状態ではなく計算で出す（2026-08-02 決定・#10）

**`CureApiService#singer?` は名義を分割して 1 つでも一致すれば通す**ので、⚠ **参加者が多い曲ほど当たりやすい。**⚠⚠ **ただし実測では単独名義が 66.4% → 62.8% と 3〜4 ポイント動くだけで、4 名義以上はむしろ減る**（名義表記が長く分割の当たりが悪いため）。**11/4 の実際のカバー 8 曲も 5 曲が単独名義。**

⚠ **「多名義ばかり」に見えた正体は本編の童謡**（`ねえねえかにどん` 8 名義・`ちからをあわせて` 7 名義・`さるがくるぞ` 6 名義）で、#63 の間引きで一緒に消える。

⚠⚠ **名義を「何人並んでいるか」で数えるのに `split_artist` を使わない**（#65）。**あちらは歌手辞書に当てるために括弧も `CV:` も割る**ので、⚠ **`パンプルル姫(CV:花澤香菜)` が 2 人、`秋元こまち(CV:永野 愛) & 水無月かれん(CV:前田 愛)` が 4 人**になる。**当てる規則と数える規則は別物**（数えるほうは `CureApiService.credit_count`）。

⚠ **区切りに `and` を入れない。**実データに `and` を含む名義は 0 件で、しかも ⚠⚠ **Ruby の `\band\b` は非 ASCII の隣で効かない**（`つぼみandえりか` は割れない）。**効かない指定を残すと「対応済み」に見えるだけ害になる。**

⚠ **`with` / `feat.` は逆に入れる**（2026-08-15・#67 のレビュー指摘）。実データの名義 **15 件**に出て、⚠⚠ **全件が「単独の歌手 ＋ もう 1 組」の区切り**（`うちやえゆか with Splash Stars`）。**入れないとこの形が単独名義として重みを 2 倍もらう**＝機能の目的と逆に効く。⚠ **`\b` は使わない** — `normalize` が空白を落として `うちやえゆかwithSplashStars` になるので、`and` と同じ理由で効かない。

⚠⚠ **中黒は「括弧の外に 2 つ以上あるときだけ」区切りとみなす。**⚠ **中黒は名前の中にも入る**（`キュア・カルテット` / `ヤング・フレッシュ` / `ルールー・アムール` はどれも 1 組）ので**無条件に割ると単独名義が複数名義に化ける**が、⚠ `Machico・吉武千颯・北川理恵・ローラ・…`（8 人）は**割らないと単独名義**になる。実データではこの 2 つが中黒の数で分かれた。⚠ **括弧を落としてから数える**（`キュア・レインボーズ(五條真由美・…)` は括弧の中に構成員が並ぶだけ）。⚠ **既知の例外は `ピョートル・イリイチ・チャイコフスキー`**（1 人・中黒 2 つ）だが、⚠⚠ **カバーの母集合はプリキュア歌手に絞ってあるので届かない。**

⚠ **スラッシュの別名表記（`黒川エレン/キュアビート(CV:豊口めぐみ)`）は対応しない**（同レビューの指摘・**却下**）。⚠⚠ **カバーの母集合 323 曲に該当が 1 件も無い**（母集合の `/` 名義は 3 件で、すべて本当の複数名義）。**文字列だけでは別名と共演を見分けられない**ので、届かない規則を足さない（`and` と同じ判断）。

⚠ **この 2 点で単独名義は 211 → 206 になった**（母集合 323・実測 2026-08-15）。**5 曲が「単独名義として 2 倍の重み」をもらっていた誤り。**

#### ⚠ 間引きは seed ではなくライブの選曲側で持つ（2026-08-15・#63）

**本編から外す曲は `/live/setlist/exclude` に置く。**⚠⚠ **`seed` の `live` フラグを落とす形にしない。**

**フラグは「本編に出す曲」であると同時に「MAKOTO 本人の曲」の印**でもあり、`Setlist#pick_covers` が **「`live` に無い vocal ＝ 他の歌手の持ち歌」** としてカバー母集合を作っている。⚠ **seed から外すと、本編から消えた 8 曲がそのままカバー枠の候補になった**（実測）。⚠⚠ **「本編から間引いた本人の曲が、ゲストコーナーで他人の曲として出てくる」**という壊れ方で、⚠ **抽選の引き次第なので、たまたま出ない日には気付けない。**

⚠ **並びの都合はライブの選曲で持ち、データの区分（`live`）は触らない。**日常の曲紹介（#16）の母集合もこれで変わらない。

## ブランチ戦略

| ブランチ | 目的 |
| --- | --- |
| `main` | リリース済み安定版。clone 時に得られるブランチ |
| `develop` | 開発ブランチ。日常の作業はここ |
| `feature/{issue}` | 大きな変更・並行作業が必要なときだけ切る（squash merge） |

### リリースフロー

1. `develop` で開発・コミット
2. リリース時に `develop` → `main` へ PR を作成しマージ
3. `main` でタグを打ちリリース

⚠ **`develop` 宛の PR では `Closes #n` が効かない。**GitHub は**既定ブランチ（`main`）へのマージでしか Issue を自動クローズしない**ので、develop へのマージでは Issue が open のまま残る（2026-08-05 に #43 / #12 で確認）。**書いてもよいが、閉じるかどうかは必ず手で判断する**（ラップアップの分類ルールは下記「Issue / マイルストーン運用」）。

⚠ **`gh pr create` では `--base develop` を必ず指定する。** 省略するとリポジトリ default の `main` が base になり、未リリースの変更が黙って main に乗る（モロヘイヤで 3 件同時に踏んだ事故がある）。リリース PR のときだけ `--base main`。作成直後に `gh pr view <番号> --json baseRefName` で確認する。

## Issue / マイルストーン運用

- **Issue 駆動**。思いつきの改善は直接コミットせず、まず Issue 化する
- **「相談」と切り出された依頼は、選択肢の検討 → Issue 起票がゴール**。実装着手は明示の合図を待つ
- **スコープ確定 = GitHub マイルストーンの作成と割り当て**。docs にバージョン節を書くだけでは確定ではない

  ```bash
  gh api repos/pooza/makoto2/milestones -f title='0.2.0' -f state='open' -f description='...'
  gh issue edit <n> --milestone '0.2.0'
  ```

- **サイズラベルと重み予算**で管理する（件数では実態を反映しないため）

  | ラベル | 想定差分 | 重み |
  | --- | --- | --- |
  | `size:S` | 50 行未満 / 単発修正・docs | 1 |
  | `size:M` | 50〜200 行 / 新メソッド・契約変更 | 3 |
  | `size:L` | 200 行超 / 新機能・スキーマ変更・複数ファイル横断 | 8 |

  1 マイルストーンの目安は **20〜25 重み**。超えそうな Issue は次のバージョンへ送る。計画書は作らず、Issue ＋ マイルストーン ＋ 重み合計で管理する
- **新しいマイルストーンに着手したら最初にバージョンをバンプする**（開発中バージョンを常に識別可能にする。実行中のコードが判別できないとデプロイ・検証で事故る）
- **元要件を先送りするときは、受け皿の後続 Issue を起票するまで元 Issue をクローズしない**。「クローズ後に別途起票する」は消えるので、起票はクローズ前に行う
- **マイルストーン未設定の軽い課題は近接処理する**（重い作業の合間に片付ける）。ただし大きな設計案件はその場の雑談処理に混ぜない
- **ラップアップ時は、着地した Issue を「単純なモンキーテストができるか」で分類する** — 不可（内部最適化・純粋リファクタ）は即クローズ、可能なものは open 維持で軽いテスト観点メモだけ付ける

### リリース前レビュー

**単一のセキュリティレビューだけでは実用上の問題が取りこぼされる**（モロヘイヤ・capsicum の両方で実証済み）。以下 5 観点を独立に走らせて指摘を合流させる。

| 観点 | 焦点 |
| --- | --- |
| セキュリティ | トークン・API キーの取り扱い、シークレットの scrub、入力検証、SSRF |
| 外部 API 契約 | Mastodon API、iTunes Search API、LLM プロバイダの契約整合とレート制限 |
| 並行性・ライフサイクル | 常駐プロセス、スケジューラ、DB / キャッシュ接続、再接続、孤児プロセス |
| エラー処理・観測性 | 例外の分類、ログの個人情報漏洩、死活監視、失敗時の再通知 |
| コーディングスタイル・規約整合性 | lint、命名、表記規約（下記） |

指摘は **赤（必修＝データ破損・セキュリティ・ユーザー可視の機能不全）/ 黄（余力があれば＝単一 edge case・観測性ギャップ）/ 緑（送り＝将来の構造改善）** に分類し、赤だけ本リリースで対応する。

**機能が全台 OFF ＝ ライブ露出ゼロなら、真の赤でも非ブロック化して受け皿 Issue に繰越してよい**（モロヘイヤの Spotify OAuth で適用した判断）。

## CI（2026-07-30 決定・#6）

GitHub Actions で **`rubocop` / `rake config:lint` / `rake test`** を回す（[.github/workflows/test.yml](../.github/workflows/test.yml)）。`develop` / `main` / `feature/**` への push と、`develop` / `main` 宛の PR が対象。

- **CI に秘密情報を持たせない。** `config/local_sample.yaml` をそのままコピーして使う。**テストは WebMock で通信を遮断してある**ので、CI から実サーバーへは 1 通も飛ばない（→ コーディング規約の WebMock の項）
- `rake migration:run` も流す。マイグレーションが 0 本の間も正常終了する
- ⚠ **CI があってもローカル実行を省略しない。** 「CI が見るから」でローカルの lint / test を飛ばさない（規約どおり）
- **Dependabot**（[.github/dependabot.yml](../.github/dependabot.yml)）は **`open-pull-requests-limit: 0`**。バージョン更新の PR は止め、**セキュリティ更新の PR だけ受ける**（別枠なので届く）。締め切りまでは更新 PR のノイズを避ける。モロヘイヤと同じ方針。脆弱性アラート自体はリポジトリ設定側で有効
- ⚠⚠ **Dependabot のアラートは `develop` に修正が入っても閉じない。**⚠ **GitHub が見るのは既定ブランチ（`main`）**なので、**`develop` → `main` のリリースまで open のまま残る**（`develop` 宛の PR で `Closes` が効かないのと同じ理屈 → 上記「リリースフロー」）。⚠ **「直したのに open」を未対応と読み違えない。**実例: `json` の低リスク 1 件は **2026-08-09 に `Gemfile.lock` が 2.21.2（修正版）になっているが、`main` が 0.1.0 のままなのでアラートは open**
- ⚠⚠ **fork から来た PR では CI が自動で走らない。**このリポジトリは public なので**外部からの PR が届きうる**（実例: #56・`shin4141`・2026-08-14）。⚠ **workflow の実行には手動承認が要る**ので、**チェックが空なのを「CI が緑」と読み違えない。**⚠ **承認する前に差分を読む**（承認＝自分のリポジトリの CI で他人のコードを走らせること）。⚠⚠ **承認は run 単位なので、コミットを積まれるたびに要る** — #56 は 2 コミットとも `action_required` で溜まっていた。**古いほうは承認せず、最新の head だけ承認して緑を確認し、squash merge した**（2026-08-15）

- **ログは syslog に出る**（ident は `makoto2`。`journalctl -t makoto2`）。ginseng の Logger が JSON 1 行で吐く
- **`/logger/mask_fields` が秘密情報の唯一の正本。** ログのマスクと `makoto config` の伏せ字が同じリストを見る。⚠ このリストは fail-open な rescue の内側で読まないこと（読めなければ「マスク対象ゼロ ＝ 素通し」になる）
- **`bin/makoto_daemon.rb` が標準出入力を `/dev/null` に落とすのは `start` / `restart` のときだけ。** 常駐時の `Errno::EPIPE` は避けつつ、`stop` / `status` の出力は監視やスクリプトから読めるようにしてある
- **スケジューラはハートビートを 1 本持つ**（`/scheduler/heartbeat/interval`）。登録した投稿の数を一緒に出すので、「常駐しているが何もしていない」状態が検知できる
- ⚠⚠ **枠ごとにジョブを登録しない。**ライブは 8 時間で 240 枠あり、枠の数だけ登録すると日をまたぐたびに登録し直すことになる（＝進行位置を状態として持つのと同じ）。**`/scheduler/tick` の間隔で叩き、そのつど「いま枠の頭か」を時刻から計算する。**⚠ **枠の間隔は tick より長いこと**（短いと 1 回の叩きが複数の枠に跨がって取りこぼす。`PostingJob` が起動時に弾く）
- ⚠ **投稿の冪等キーは枠の頭の時刻から作る**（`{名前}-{枠の時刻 UTC}`）。tick が重なっても、再起動で同じ枠をもう一度処理しても、Mastodon 側が畳む。⚠⚠ **同じ枠なら本文が変わっても 1 通**（抽選をやり直しても二重投稿にならない）
- ⚠⚠ **常駐の開始直後に 1 回叩く**（`Scheduler#schedule_posts`・2026-08-08・#47）。`every` は最初の間隔を待つので、これが無いと**枠の頭 ＋ tolerance の内側で再起動した枠が落ちる**。⚠ **位置の計算は正しいのに、再起動直後にそれを呼ぶ機会が無い**という形で「落ちて戻ってきても位置がずれない」が最後の 1 行で効いていなかった。⚠ **投稿済みの枠をもう一度処理しても冪等キーで畳まれる**ので、叩いて困る経路は無い
- ⚠⚠ **繰り返しの登録が先、初回の tick が後。**初回の tick は投稿を伴うので **HTTP の再送で秒単位に伸びうる**。⚠ **逆順にすると、伸びている間に次の枠が tolerance ごと過ぎて落ちる**（ライブの枠は 2 分間隔）
- ⚠ **`bin/makoto_daemon.rb start` は前景で走る。**背景化するのは `restart`（`fork` ＋ `setsid` ＋ `detach`）。**デプロイ・監視から起動するときは `restart` を使う**（→ #15）

## コーディング規約

### Ruby（RuboCop）

モロヘイヤ・tomato-shrieker と同じ方針を引き継ぐ。

- **`Layout/EndAlignment: EnforcedStyleAlignWith: variable`** — 見栄えのための位置揃えを自動検出する（下記のインデント方針）
- **`Style/RedundantReturn: Enabled: false`** — 暗黙の return を使わない方針と衝突するため無効化する
- 収集スクリプト（[seed/](../seed/)）は Python のまま残してよい。RuboCop の対象外

言語に依存しない規約:

- **インデントは常に論理的な 2 スペース。** 見栄えのための位置揃え（代入の右辺に制御式を置いて深くインデントする等）は使わない。インデントの深さはコードの論理構造だけを反映する
- **暗黙の return を使わない**（Ruby を選ぶ場合、メソッド末尾でも `return` を省略しない）
- **lint / test を「環境が壊れている」で迂回しない。** 依存導入・環境修復をしてから必ず実行する。「CI が見るから」でローカル実行を省略しない
- **機能追加・バグ修正には対応するテストを書く**（CI で実行可能な範囲で。外部 API 依存のテストは無理に書かなくてよい）
- ⚠ **WebMock は `require` だけでは有効にならない。`WebMock.enable!` を呼ぶまで、`stub_request` も `disable_net_connect!` も無言で素通りする。** MAKOTO は投稿するボットなので、これを忘れるとテストが**実サーバーに書き込む**（2026-07-30 に実際にステージングへ 10 通投げた）。`TestCase#setup` で有効化し、**「stub していないリクエストが `WebMock::NetConnectNotAllowedError` になる」こと自体をテストする**
- ⚠ **再送する経路で外部へ書き込むときは冪等キーを持つ。** MAKOTO は無人で投稿し続けるので、`HTTP#retryable?` の再送は「投稿が二重に出る」経路でもある（Mastodon が受理した後に応答だけ失われると、再送が同じ投稿をもう 1 つ作る）。1 回の論理的な投稿につき `Idempotency-Key` を 1 つ作り、**全試行で使い回す**。テストは「キーが付いている」ではなく**「同じキーが全試行で飛ぶ」**ことを見る（前者では 3 通投稿される事故を検知できない）
- **運用上必須の設定は JSON Schema の `required` に入れる。** 親キーだけを `required` にしても、中身が欠けた設定は `rake config:lint` を通り抜け、その設定を使う瞬間に初めて落ちる
- ⚠⚠ **省略できる設定は `optional_config` で読む。素の `config[]` を使わない**（2026-08-15・#77）。⚠ **`Ginseng::Config#[]` はキーが無ければ例外を上げる**（既定値へのフォールバックが無い）ので、**「設定を消せば止まる」と説明した設定を素で読むと、消した瞬間に落ちる**
  - ⚠⚠ **`rake config:lint` は通る**（schema が必須にしていないため）。**使う瞬間まで分からない**
  - ⚠ **落ち方が 2 通りに分かれるのが厄介** — **起動時に読むもの**（`/live/hashtag`）は常駐が起動せず監視が拾えるが、⚠⚠ **枠の中で読むものは `PostingJob` の rescue に飲まれ、「登録ジョブ 5 で健全」のまま 160 枠が沈黙する**
  - ⚠ **`rescue` で受けない。**キーの有無だけを見て、⚠⚠ **値を読む側の失敗は握り潰さない**（`rescue` にすると設定パスの typo が同じ穴に落ちる → 上記「fail-open な rescue の内側で設定値を読まない」）
  - ⚠ **テストは「キーはあるが空」ではなく、本物の「無い」を見る**（`test/optional_config.rb`）。⚠⚠ **旧 `test_excludes_nothing_without_the_setting` は名前に反して空配列しか見ておらず、素通ししていた**
- **fail-open な `rescue` の内側で設定値を読まない。** 設定パスの typo が例外として飲まれ、ガードが恒常 no-op になる（モロヘイヤで実際に踏んだ「守っているつもりで無防備」という静かな穴）。ガードのパラメータは定数化するか rescue の外で評価し、**「実際にブロックする」正テストを必ず書く**
- ⚠ **例外メッセージを埋め込むときは `error_message` を通す。** Sequel / SQLite の例外は **ASCII-8BIT** で上がるので、台詞のような非 ASCII を含む SQL が失敗すると `"...: #{e.message}"` が `Encoding::CompatibilityError` になる。**エラー処理そのものが落ちて本当のエラーが隠れる**（無人で動くボットでは誰も気付けない）
- ⚠ **テストの共通処理は `setup` メソッドではなくコールバック（`setup do ... end`）で登録する。** メソッドにすると、サブクラスが `setup` を定義して `super` を忘れた瞬間に外れる。**忘れても落ちない**ので素通しに気付けない（WebMock の通信遮断で実際に起きうる形だった）
- **秘密情報はログに出さない。** OAuth 認可コード・アクセストークン・API キーは scrub 対象に入れる

## LLM プロバイダとモデル（2026-07-30 決定・#3）

**Anthropic Claude / `claude-opus-5`。全機能で同じモデルを使う。**

- **公式の Ruby SDK がある**（`gem install anthropic` → `Anthropic::Client.new`）。Messages API・ストリーミング・プロンプトキャッシュ・ツール呼び出しが揃っており、「LLM だから Python」はクライアント層では成り立たない
- **機能ごとにモデルを変えない。** キャラの一貫性が第一の評価軸である以上、語り口の基準を 2 つ持つのは目的に逆行する。コスト最適化は必要になってから

### コーパスはプロンプトに全部載る（実測）

**応答に使える台詞 561 件で 6,969 文字**（平均 12 文字・最長 70 文字）。`quote` 956 件と `message` 388 件を合わせても 3 万文字弱で、**コーパス全体がシステムプロンプトに収まる**。

⚠ **ベクトル検索も RAG 基盤も要らない。** これで「Ruby の再考の引き金」は実質消えた（→ 上記スタックの節）。

### 実装上の要点

- **プロンプトキャッシュを使う。** コーパスをシステムプロンプトの先頭に固定し、末尾のブロックに `cache_control` を置く。ライブ当日は 2〜3 分間隔で投稿するので **1 時間 TTL** が効く（8 時間 194 曲で概算 $10 → $3）
- ⚠ **Ruby SDK は `system_:`（末尾アンダースコア）** — `Kernel#system` との衝突を避けるため。`system:` ではない
- ⚠ **レスポンスの `.type` は Symbol**（`:text` であって `"text"` ではない）
- ⚠ **`stop_reason` が `:refusal` のことがある。`content` を読む前に必ず分岐する。** 安全性の分類器が働くと HTTP 200 で本文が空になるので、`content[0]` を無条件に読むコードは壊れる。**MAKOTO は無人で投稿し続けるので、拒否されたら定型文にフォールバックして黙って落ちないようにする**
- サーバー側フォールバック（`fallbacks: "default"`）を既定で有効にする
- **API キーは `config/local.yaml`（gitignore）に置き、ログの scrub 対象に入れる**

### ⚠ Claude Max の契約枠では API は使えない

**Max プランは claude.ai / Claude Code / デスクトップアプリ向けで、API 利用は含まれない。** MAKOTO が API を叩く分は Developer Platform 側の従量課金になる（別勘定）。「Max が余っているからその枠で」は成立しないので、API クレジットを別に用意する。

そのうえで、**実行時に LLM を呼ぶ範囲を絞れば従量課金はかなり小さくできる**。

| 機能 | 実行時に LLM を呼ぶか |
| --- | --- |
| 朝挨拶 | **原則ノー。** 前もって用意した原稿を配信する（#12 の上書き機構）。素材は `morning` 237 件 |
| バースデーライブの告知・進行 | **ノー。** 台本は前もって書く。11/1 の予告も同じ |
| 曲紹介 | 紹介文テンプレート ＋ 曲データで足りるなら不要。語り口に幅が欲しいところだけ呼ぶ |
| チャットボット | **イエス。** ここだけは実行時に必要 |

原稿・台本の執筆そのものは **Max の枠内で対話的にやればよい**（Claude Code や claude.ai で書いて `message` に流し込む）。**API 課金が必要なのは実質チャットボットだけ**になる。

| --- | --- | --- |
| キャッシュ無し・561 件同梱 | 約 $0.065 | 約 150 回（1 日 5 回） |
| キャッシュ読み・561 件同梱 | 約 $0.011 | 約 900 回（1 日 30 回） |
| キャッシュ無し・150 件に絞る | 約 $0.020 | 約 500 回（1 日 16 回） |

⚠ **プロンプトキャッシュはチャットボットではライブほど効かない。** メンションが散発的だと 5 分 TTL が切れ、毎回キャッシュ書き込み（1.25 倍）が乗って**かえって高くつく**。効くのは会話がバースト的に来るときだけで、定時投稿とは前提が違う。

**歯止めは 3 つ用意する。**

1. **同梱する台詞を絞る** — 効果が一番大きい。`form` と `priority`（1〜5 に分布）で選抜する。**何件同梱すれば語り口が保てるかは #19 で実測して決める**
2. **1 日あたりの応答回数に上限を持つ**（コード側・#18）
3. **Console 側に支出上限を設定する**（運用側）

### LLM が落ちてもライブは走る

**8 時間の枠は LLM の可用性に依存させない。** 生成に失敗したら台詞コーパスから定型で投げるフォールバックを最初から用意する（→ #10 / #13）。

## データストア（2026-07-30 決定・#4）

**SQLite ＋ Sequel。**

旧実装は PostgreSQL で `ginseng-postgres`（pg + Sequel）も手元にあるが、**保持するデータが小さく、常駐プロセスを増やしたくない**ため採らない。

| データ | 量 | 性質 |
| --- | --- | --- |
| 台詞コーパス | 1,340 行 | 更新は稀・読み取り専用に近い |
| 曲 | 4,305 行 | 同上 |
| 投稿履歴 | 増え続ける | 重複回避のための書き込み |

- **常駐プロセス 1 本という決定と整合する。** PostgreSQL を建てると監視対象と「ライブ 8 時間の間に落ち得るもの」がもう 1 つ増える
- **Sequel を挟むので、後から PostgreSQL へ移せる**（`ginseng-postgres` も Sequel ベース）
- 2GB CT に対して圧倒的に軽い

### ⚠ バックアップは `VACUUM INTO` で取る

**稼働中の SQLite ファイルを生でコピーすると壊れた写しになる。** `writersbase-tools` の `google_drive_backup` は `rclone sync` でパスを生コピーするため、そのままでは使えない（chubo2 が Uptime Kuma で同じ判断をしている）。**`VACUUM INTO` で一貫スナップショットを作ってから上げる。**

コーパスは唯一の代替不能な資産なので、バックアップ手順は #8 の完了条件に含める。
