# makoto2 開発ガイド

このファイルがプロジェクトのルール・構造・履歴の**正本**。メモリ（`MEMORY.md`）はポインタと補足だけを持つ。

## プロジェクト概要

**MAKOTO** は、剣崎真琴（キュアソード / CV: 宮本佳那子）をモデルにした AI マスコットボット。Mastodon サーバー「キュアスタ！」（precure.ml）で稼働する。

- **アカウントは継続使用**: [@makoto](https://precure.ml/@makoto)（44,161 投稿・最終投稿 2026-06-24）
- **コードは作り直し**: 旧実装 [pooza/makoto](https://github.com/pooza/makoto)（最終コミット 2024-11-10）はアーカイブ済み。**使い回さない**
- **言語・スタックは自由**（Ruby 縛りなし）。未決＝下記「未決事項」
- **稼働先は旧サーバー（lbock）非依存**。専用 CT（2GB）に隔離して建てる。旧実装は本番サーバー（lbock）に同居して孤児プロセスを撒いた前科があるため、同居させない。**開発用 CT (`bydo`) は 2026-07-30 に用意済み。本番も pve 内にもう 1 CT 建てる**（→ 下記「実行環境」）
- **入出力は非対称にする**（旧 makoto と同じ）。**出す側は抽象化し、読む側は Mastodon に決め打つ** → 下記「入出力の非対称性」

**ハドラーブロス**（[@hadlarbot](https://mstdn.delmulin.com/@hadlarbot)・895 投稿・最終 2025-01-06）は **makoto2 のスコープ外**。要件が MAKOTO とまったく異なり、**必要なのはチャットボットの部分だけで、急いでもいない**。同じリポジトリに同居させると、絞り込んだ 4 機能に無関係な分岐を抱え込むだけになる。**復活させるときは別リポジトリで別立てにする。**

## 機能スコープ: 4 つに絞る

**「キャラのぶれ」を無くすための絞り込み**であって、単なる工数削減ではない。この 4 つ以外は当面やらない。

1. **曲紹介**
2. **朝挨拶**（特定の日は、前もって用意した原稿で上書きできる）— ⚠⚠ **「朝の冠番組に出演していて、その最初の挨拶をしている」というテイ。**定型挨拶＋他愛もない日常話という構造は**宮本さんの「キッズ劇場」由来**で、⚠ **この由来はコードにもデータにも残っていない**（→ [makoto-persona.md](makoto-persona.md)）
3. **チャットボット**
4. **11/4 バースデーライブ** → [birthday-live.md](birthday-live.md)

旧実装で Issue が立っていたが未実装だった機能（曲の管理、WebUI からの辞書更新、キーワード学習）は、上記に必要な範囲だけ作る。**機能を増やす提案をするときは「キャラの一貫性を損なわないか」を先に述べる。**

## 設計方針

### キャラの一貫性を第一の評価軸にする

旧実装は台詞コーパスを**そのまま返していた**とみられ、文脈を無視した投稿が実際に出ていた。これが「キャラのぶれ」の正体である可能性が高い。作り直しでは**コーパスを LLM の few-shot / RAG 素材として使う**方式に変える（詳細と実データは [makoto-legacy.md](makoto-legacy.md)）。

⚠ **語り口だけを見ても足りない。****本編に無いことを語っていないか**も評価軸に入れる。真琴は孤児だが**出自を語る台詞がコーパスに 1 件も無い**ので、LLM に任せると設定を創作する。人物設定と「語ってよい範囲」は [makoto-persona.md](makoto-persona.md) を正本にする（宮本佳那子さんのパーソナリティが混じって扱われてきた理由もそこ）。

### SNS 本体を改造しない

モロヘイヤの設計方針をそのまま継承する。MAKOTO も **Mastodon 本体（フォーク含む）に手を入れずに、公開 API と webhook の外側で完結させる**。本体パッチが増えるほど upstream 追従の工数と衝突リスクが膨らむ。

### プリキュアの情報は cure-api から REST で取る（2026-07-30 決定）

⚠ **rubicure を直接使わない。** シリーズ一覧のようなプリキュアの基礎情報は、[cure-api](https://github.com/pooza/cure-api) の REST エンドポイントから取得する。

- **経緯**: rubicure は上流が **Ruby での実装そのもの**に軸足を置いており、**作品のデータを充実させる**方向とは関心が異なる。cure-api はその受け皿として作られたもので、**MAKOTO が必要とするのは後者**。参照すべき正本は gem ではなく cure-api の側にある
- **したがって、作品の情報が足りないときは MAKOTO 側に抱え込まず、cure-api を伸ばす。** シリーズ名や放送年をこのリポジトリにハードコードし始めたら、正本が 2 つに割れた合図
- 実務上も、ライブラリを抱え込むと同じデータの写しがもう 1 つ増え、更新のたびに MAKOTO 側の再デプロイが要る。cure-api は既に公開されていて（`https://cure-api.precure.ml`）、キュアスタ！でも使っている
- ⚠ **cure-api に載せるのはプリキュアの情報だけ**（2026-08-08 整理）。cure-api は元々**プリキュア淑女録スプレッドシートにアクセスする API デーモン**なので、⚠ **スプレッドシートで管理したいプリキュアのデータ（旧実装が持っていた妖精など）は cure-api を伸ばす**。⚠ **MAKOTO が Google Sheets API を直接叩く形にはしない**（サービスアカウントを持つ箱を増やさない）
- ⚠⚠ **MAKOTO の原稿は cure-api に載せない。**原稿はプリキュアの情報ではなく、載せると cure-api の役割が「プリキュアの情報を返す API」から外れる。**必要になったら別の方法を考える**（→ #50）
- ⚠⚠ **cure-api に認証を足す前提の設計をしない**（2026-08-08 方針）。cure-api は**認証を持たない公開 API**として運用する。⚠ **したがって「認証を掛ければ非公開データも置ける」という逃げ道は無い。****非公開のものは cure-api の外に置く**（未公開の台本がその代表例）

| エンドポイント | 返るもの |
| --- | --- |
| `GET /series` | `[{"key": "dokidoki", "title": "ドキドキ！プリキュア"}, ...]`（2026-07-30 時点で 24 件） |
| `GET /series/index` | `key` の配列だけ |
| `GET /series/:key` | そのシリーズの詳細 |
| `GET /singers` | プリキュア歌手の名義（`name` ＋ グループの `members`。2026-08-13 時点で 50 名義）。⚠ **ライブのゲストコーナーが母集合を絞るのに使う**（→ 下記「ライブの並びは抽選ではなく整列」） |

⚠ **名義の表記揺れは MAKOTO 側で吸収する**（`CureApiService.normalize`＝NFKC ＋ 空白除去。cure-api の `Datasource.normalize_name` と同じ規則）。⚠⚠ **スプレッドシートは「宮本 佳那子」、iTunes 由来の曲データは「宮本佳那子」。**ここが噛み合わないと 1 件も一致しない。

収集スクリプト（[seed/](../seed/)）も同じ方針に揃える。**ローカルの作業コピーのパスを埋め込まない**（`/home/pooza/repos/rubicure/...` のような書き方は、他の端末で動かない）。

### 入出力の非対称性: 出す側は抽象化、読む側は Mastodon 決め打ち（2026-07-31 整理）

**旧 makoto と同じ仕様。**投稿と受信で扱いを変える。

| 向き | 経路 | 抽象化するか |
| --- | --- | --- |
| **出す**（投稿） | モロヘイヤの **Slack 互換 webhook**（`POST /mulukhiya/webhook/{digest}`）／ Mastodon API 直 | **する。**Slack 互換 webhook を実装した他サービスにも同じコードで向けられる |
| **読む**（メンション検知） | Mastodon の **Streaming API**（WebSocket） | **しない。Mastodon に決め打つ。**読む側は SNS 固有の仕様に踏み込むので、抽象化しても得るものが無い |

⚠ **どちらも outbound。**「inbound は開けない」（→ 下記「実行環境」）と矛盾しない。webhook は**送りつける側**であって、MAKOTO が受け口を持つのではない。Streaming API も MAKOTO 側から張る WebSocket 接続。

⚠ **「モロヘイヤの webhook を受ける」という書き方をしない。**向きが逆に読めて、inbound を開ける話だと誤解される（実際に一度誤読された）。

#### 🔴 投稿はモロヘイヤを経由する（2026-08-19 決定・#124）

🔴 **`X-Mulukhiya` を送らないことで経由する。**⚠⚠ **ヘッダを付けたほうが「経由しない」** — モロヘイヤ側の nginx が

```nginx
map $http_x_mulukhiya $mulukhiya_backend {
  default http://localhost:3008;   # モロヘイヤ
  "~.+"   http://localhost:3000;   # Mastodon 直（自己ループ防止）
}
```

で振り分けており、**付いている要求を Mastodon 本体へ直に流す**（モロヘイヤ自身の投稿が自分に戻らないようにするため）。

🔴 **⚠⚠ ginseng-fediverse の既定は「付ける」（`@mulukhiya_enable = false`）。**⚠ **素で継承すると黙って迂回する** — **2026-08-19 の当日通しリハーサル 162 投稿が 1 本もモロヘイヤを通っていなかった**（dev25 の access log で実測）。⚠⚠ **投稿は 200 で返り、ログにも成功としか出ていなかったので、3 週間気付かなかった。**🔴 **経路の間違いは投稿の失敗として現れない。**

- ⚠⚠ **迂回するとタグ付け（`default_tag` / `dictionary_tag` / `tagging`）・URL 正規化・画像添付が掛からない。**⚠ **旧アカウントの朝挨拶に 10 年付いていた `#precure_fun` はモロヘイヤが付けたもの**で、**キュアスタ！のタグ＝コミュニティ側の導線**（→ 下記「コミュニティ・文化に資する」）
- ⚠⚠ **MAKOTO が自分で付けるタグは `/live/hashtag` の 1 つだけ。**⚠ **あとはモロヘイヤに任せる**（**ライブの 160 投稿にモロヘイヤのタグが付くこと自体は、そのままでよい**）
- ⚠⚠ **「最終行をタグだけの行にする」の根拠は Mastodon の仕様であって、モロヘイヤではない**（2026-08-19 訂正）。⚠ **タグの直前の空行はモロヘイヤが勝手に入れる**ので、**MAKOTO 側では足さない**（→ `HashtagSource`）
- ⚠ **枠ごとに経路を分ける仕組みは持たない。**設定は `/mastodon/mulukhiya`（boolean）の 1 つ
- ⚠⚠ **切り戻しは `config/local.yaml` に `mulukhiya: false` の 1 行。**⚠ **当日にモロヘイヤ側が不調なら Mastodon API 直へ戻せる**
- ⚠ **`optional_config` で既定値に逃がさない**（schema の `required`）。⚠⚠ **消しただけで経路が静かに戻る形を作らない**（#77 の裏返し）
- ⚠⚠ **`verify_credentials` は経路の設定に関わらず常に直。**⚠ **「モロヘイヤが落ちている」が「トークンが死んでいる」に化けると、当日いちばん困る**（→ #106）

##### ⚠ webhook の前倒し（#30 本体）ではなくこちらを選んだ

⚠ **11/4 までにどちらか必須**という前提で比較した（2026-08-19）。

| | webhook 前倒し（#30 本体） | ✅ `X-Mulukhiya` を送らない |
| --- | --- | --- |
| 投稿 URL | ⚠⚠ **返らない**（`makoto post` とログが壊れる） | そのまま返る |
| 可視性 | ⚠⚠ **投稿ごとに指定できない**（アカウント単位に固定・pooza/mulukhiya-toot-proxy#4599 待ち） | 本文と一緒に通る |
| `Idempotency-Key` | 渡す手段が無い | ⚠ **転送されない**（pooza/mulukhiya-toot-proxy#4598 待ち） |

⚠⚠ **冪等キーの穴はどちらを選んでも同じ**（プロキシ経路もヘッダを転送していない）。⚠ **#109 の `claim` でプロセス内の重なりは塞がっている**ので、**残るのは 1 回の `post_status` の中の HTTP 再送だけ。**

⚠ **#30 は閉じない。**出力先の抽象化そのもの（Slack 互換 webhook を実装した他サービスへ同じコードで向けられること）は残る話で、⚠⚠ **#124 はその前提を実運用に合わせた修正**。

#### ✅ 画像添付は実装しない。URL を貼って SNS のプレビューカードに任せる

**曲紹介のアートワークは、URL を貼れば Mastodon 側が OGP のプレビューカードとして補完する**（→ [track-corpus.md](track-corpus.md)）。⚠ **これは SNS 側の機能なので、出力先を抽象化しても失われない。**

🔴 **⚠⚠ 2026-08-19 に投稿がモロヘイヤ経由になった（#124）ので、これは「webhook を入れたら起きうる」話ではなく、いま起きる話。**⚠ **`ItunesImageHandler` が画像も添付するため二重になりうる**（`handle_pre_webhook` は `handle_pre_toot` に委譲するので、経路が webhook でも走る）。**#16 で実機確認し、必要ならモロヘイヤ側で切る。**

#### ⚠ ストリーミング受信は「里帰り」になる

**モロヘイヤの `Listener`（`app/lib/mulukhiya/listener.rb`）は旧 makoto から移植された実装。**makoto2 で書くと、出ていったものが戻ってくる形になる。

- **参照するのは旧 makoto ではなくモロヘイヤ版。**移植後にモロヘイヤ側で手が入っており（指数バックオフ・シグナル処理・最終受信時刻のハートビート）、本番で揉まれている。旧実装はアーカイブ済みで、そちらを掘る理由が無い
- **「コードは作り直し・旧実装は使い回さない」とは矛盾しない。**スタックの決定で「フレームワークは引き継ぐ」としたのと同じ扱いで、**キャラの一貫性に関わらない配管**だから。逆に、台詞の使い方（そのまま返す）は引き継がない
- ⚠ **モロヘイヤ版をそのまま持ってこられない。**`EventMachine` のイベントループと最終受信時刻の Redis 保存を前提にしており、MAKOTO は**常駐 1 本＋内蔵スケジューラ・Redis 無し**。同居のさせ方は設計時に決める

### 管理操作は CLI で行う（WebUI の管理コンソールは作らない）

旧実装は `/makoto` に管理コンソールを持っていたが、**パスを知る利用者は運用者ひとりだった**うえ、退役後も nginx に残骸を残した（→ [makoto-legacy.md](makoto-legacy.md)）。makoto2 では管理コンソールを作らず、**原稿・辞書・曲データの更新といった運用操作はコマンドラインのサブコマンドとして実装する**。

- 認証・セッション・画面という付随物を持ち込まずに済む
- SSH 越しに実行でき、デプロイ・監視と同じ経路に乗る
- 旧実装で Issue が立っていた「WebUI からの辞書更新」も、**WebUI ではなく CLI として作る**

なお「WebUI」は利用者向けの機能を指す語としては引き続き使う（表記規約）。ここで作らないと決めたのは**運用者向けの管理コンソール**。

#### ✅ 原稿の登録も CLI のままでよい（2026-08-14 判断）

**旧実装はスプレッドシートで原稿を編集していた**（レイアウトは `message` テーブルと完全に一致。`type` / `feature` / `month` / `day` / `message` / `data`）。⚠ **PostgreSQL だったので、手元の GUI からサーバーのデータに繋げた。**SQLite は原理的にそれを持てない。

⚠⚠ **しかし「本番の DB を GUI で触る」は、この設計と正面衝突する** — 管理コンソールを作らない / inbound は開けない / **稼働中の SQLite を生でコピーしない**。

**そのうえで、CLI のままでよいと判断した。手で書く頻度が低いため。**

| | 頻度 | 手段 |
| --- | --- | --- |
| **特定日の原稿**（元日・バレンタイン・エイプリルフールのおふざけ等） | ⚠ **年 6 回程度** | **手で書く。**CLI ＋ ファイル取り込み（#50）で足りる |
| **`morning`（他愛もない日常話）** | ⚠⚠ **飽きられない量が要る** | **生成で埋める**（→ #17。⚠ **事前生成なので人が読んで落とせる**） |

⚠ **「登録が大変」と感じていたのは後者だけ。**⚠⚠ **そちらは登録の道具ではなく、生成と選別の問題**なので、GUI もスプレッドシートも要らない。

##### ✅ 台本の置き場は [pooza/makoto-scripts](https://github.com/pooza/makoto-scripts)（private・2026-08-15・#50）

⚠⚠ **`var/script/` に置いていた台本を移した。**⚠ **`var/` は gitignore 対象で、この端末にしか無かった** — **原稿は `message` テーブルの行で DB も git 管理下に無い**ので、⚠⚠ **`bydo` に入れた台本が本番へ運ばれない。**

- ⚠ **makoto2 は public なので、投稿前の台本をこちらにコミットもできない**（ネタバレ防止）。**だから private リポジトリに分けた**
- ⚠ **private にした理由は「秘密だから」ではない。**⚠⚠ **したがって資格情報や鍵はあちらにも置かない**（cure-api で決めた「認証を掛ければ非公開データも置ける、という逃げ道は無い」と同じ考え方）
- **取り込みは `bin/makoto message import ~/repos/makoto-scripts --prune`。**⚠ **何度流してもよい**（`slug` で upsert）。⚠⚠ **`--prune` は `slug` を持つ行しか消さない**ので、`makoto message add` で足した原稿と旧ダンプ 388 件には触らない
- ⚠⚠ **本番用の台本は必ずあちらを正本にする。**⚠ **`var/script/` に複製を残さない**（当日どちらが入っているか分からなくなる）。リハーサル用の使い捨ては置いてよい
- ⚠⚠ **`makoto message add` で足した原稿は `--prune` で消えない**（`slug` を持つ行しか消さないため）。⚠ **取り込みで足した版と二重になり、`MessageSelector` がどちらかを乱択する**
  - ⚠ **2026-08-15 に実際に踏んだ** — 予告 3 本が `bydo` の DB に `slug` 無しで存在し、正本から取り込んだ 3 本と合わせて**同じ日に 2 本**になった。**手で消すしかない**（`makoto message remove ID`）
  - ⚠⚠ **原稿は DB の行なので、ホストごとに中身が違う。**⚠ **「手元に無い＝どこにも無い」ではない。**逆に**「`bydo` にある＝本番にもある」でもない**（この 3 本は本番には無かった）。**確認するときは必ず対象のホストで見る**
- ⚠ **語りの register が 3 つある**ことを、あちらの README に書いた — **自分について＝寡黙 / ファンに向けて＝言葉が増える / ⚠⚠ 他の歌手について＝敬意を向ける（敬語）**

### コミュニティ・文化に資する

### プロセスの寿命を設計に含める

旧実装は 2026-06 に**孤児プロセスが 11 日分たまり swap を 800MB 占有**し、同居していた本番サーバーの投稿レイテンシを劣化させた。停止・再起動・死活監視を後付けにせず最初から設計に含める。

⚠ **monit の `exec` は argv に分割されるため `&&` 以降が黙って捨てられる。** 本番 3 台の自動復旧がこれで長期間死んでいた実例がある。復旧コマンドはラッパースクリプトに逃がす。

### 死活監視は「生きているか」と「仕事をしているか」を分ける（2026-08-08 決定・#15）

⚠⚠ **systemd の `Restart=always` はプロセスの死しか見ない。**⚠ 実際に **2026-08-05 から 08 までの 3 日間、常駐は生きたまま `jobs: 0`（投稿の登録が 0 本）だった。**プロセスの生死だけを見る監視ではこれを検知できない。

- **監視の口は `makoto status`**（`Makoto::Health`）。⚠ **終了コードで返す** — **`0` 健全 / `1` 異常（復旧させる）/ `2` 警告（人が見る）**。⚠ **箱の外（Kuma）からは HTTP で叩く**（→ 下記「監視の口は HTTP で外から叩く」）
- 見るのは 6 つ。**生死** / ⚠ **登録された投稿の数**（0 は異常）/ ⚠ **ハートビートからの経過**（止まっていればスケジューラが死んでいる）/ 🔴 **最後に tick が回った時刻**（→ 下記）/ ⚠⚠ **連続して落ちた投稿の本数**（警告）/ **孤児プロセス**
  - 🔴 **その 6 つは「判定」の話で、`makoto status` の画面は 2026-08-22 まで 5 つしか出していなかった**（#150 ＝ #107 の黄 C1・**3 観点が独立に指摘した**）。⚠⚠ **`Health#errors` は `ticked_at` を見ているのに、人が叩くコマンドが見せていない** — ⚠ **赤の理由が画面から読めない形だった**
  - ⚠⚠ **8/15〜10/31 は 1 本も投稿しないので `posting` は当てにならない。**⚠ **その 2 か月半に「動いている」を確かめる唯一の手掛かりが tick**
  - ⚠ **痕跡が無いときに `never` で終わらせない** — 🔴 **初回の tick は枠を回し終えるまで痕跡を書かない**ので、⚠⚠ **正常な起動直後と本物の詰まりが画面上で同じに見える。****何からの猶予を数えているのか（`started_at`）を一緒に出す**
- 🔴 **ハートビートと tick は別に見る**（2026-08-16・#80 の黄 7）。⚠⚠ **ハートビートは tick とは別の rufus ジョブ**なので、⚠ **tick 側だけが詰まっても痕跡は更新され続ける** — **「生きているが仕事をしていない」を見るための痕跡が、まさにその状態で健全を返していた**
  - ⚠ **`Scheduler#tick` が終わるたびに `ticked_at` を書く**（`Heartbeat.record_tick`）。⚠⚠ **投稿が 1 本も出ない枠でも書く** — ここで見たいのは**枠を見に行けているか**であって、投稿の成否は別の痕跡が持つ
  - ⚠ **記録するのは「終わった時刻」。**⚠⚠ **始めた時刻にすると、90 秒かかった tick が「90 秒前に回った」ことになり、詰まりを短く見せる**
  - ⚠⚠ **閾値を tick の間隔（10s）から導かない**（`/scheduler/tick_stale` = 5m）。⚠ **1 回の tick は投稿の再送で 90 秒以上かかりうる**ので、間隔の倍数にすると誤報する。⚠ **rufus の `every` は重なって走る**（詰まった 1 回が後続を止めない）ので、**「何分止まったら異常か」で決める**。⚠ **5 分なのはライブの枠間隔（3 分）を基準にしたから** — **1 枠飛ばした時点で気付ける**
  - ⚠ **これは `errors`（＝ 1・復旧させる）。**⚠⚠ **投稿の失敗が警告どまりなのとは逆で、こちらは再起動で直りうる**
  - ⚠ **痕跡が無いのは「一度も回っていない」。**常駐は登録の直後に 1 回叩く（→ `Scheduler#schedule_posts`）ので、**生きているのに無いのは異常**
  - 🔴 **ただし基準は「最後の tick」と「起き上がった時刻」の新しいほう**（2026-08-18・PR #98 の Codex 指摘）。⚠⚠ **監視の口は初回 tick より先に開く**（`MakotoDaemon#start`）のに、⚠ **`tick` が痕跡を書くのは枠を全部回し終えたあと** — **起き上がっただけで `/healthz` が赤くなる**形だった。⚠⚠ **落ちて 5 分以上空いてから戻る場合も同じ**で、**前回の稼働が残した古い `ticked_at` のせいで戻った瞬間から赤い**
    - ⚠ **`Heartbeat.record_start` を口を開ける前に呼ぶ。**⚠⚠ **猶予を過ぎればどちらの基準でも赤い**ので、上の検知は緩まない
    - ⚠ **窓が長いのは tick だけ。**`heartbeat is stale` / `no posting job` は `first: :now` のハートビートがミリ秒で消す
    - ⚠⚠ **いま `/healthz` を叩いて再起動する仕掛けは無い**（`rubicon` は systemd の `Restart=always` だけで monit は入っていない）ので**再起動ループにはならなかった**が、⚠ **Kuma がデプロイのたびに鳴り、`makoto status` も 1 を返していた**
  - ⚠ **既定値に逃がさない**（`optional_config` を使わない）。**設定を消しただけで検知が静かに消える形にしない**（#77 の裏返し）
- ⚠⚠ **「登録された本数」は「出た本数」ではない**（2026-08-15・#78）。`jobs` は**起動時に決まる定数**なので、⚠ **トークンが失効しても `source` が毎回落ちても、`jobs: 5` のまま exit 0 を返し続けた** — **160 枠が全滅しても健全に見える形**だった
  - ⚠⚠ **枠の結末を 3 つに分けて、失敗の側だけを数える**（`Heartbeat`）。**投稿できた**（数を 0 に戻す）／⚠ **本文が無い**（**何も記録しない**）／⚠ **`source` が落ちた・投稿が失敗した**（1 つ進める）
  - 🔴 **「本文が無い」を中立に置くのが肝。**⚠ **これを失敗に数えると、原稿がまだ無いだけの日が延々と警告になる**（MAKOTO は 8/15〜10/31 の 2 か月半がこれ）。⚠⚠ **逆に成功に数えると、#77 の「設定を消すと枠の中で例外が上がる」形が中立に紛れる**（その経路も本文が nil になる）。**だから `source` の失敗と空の本文を `PostingJob` の側で分けている**
  - ⚠⚠ **これは「異常（1）」ではなく「警告（2）」。**⚠ **再起動で直らないから** — 原因は**トークンの失効・設定の欠落・`source` の不具合・Mastodon 側の障害**で、どれも常駐を入れ直しても変わらない。**孤児で復旧を叩かせないのと同じ形**（#78 の起票は `errors` に置く案だったが、この理由で変えた）
  - ⚠ **この警告は時間で消えない。消えるのは「次に 1 本投稿できたとき」だけ。**⚠⚠ **時間で消える形にすると、投稿していない期間＝検証されていない期間に、警告のほうが先に消える**
  - ⚠⚠ **同じ枠を 2 度数えない。**⚠ **`Scheduler` は登録直後に初回 tick を叩いてから `every` で回す**ので、**拾う幅（既定 10 秒）の内側で同じ枠が 2 回来る。再起動が挟まれば毎回そうなる。**⚠⚠ **成功は Mastodon 側が冪等キーで畳むのに失敗だけ畳まれず、落ちた枠 1 つで閾値を 2 つ消費していた**（2026-08-15・#81 のレビュー指摘・実測）。**「投稿の側で冪等にしたものは、観測の側でも冪等にする」**。🔴 **その「畳む」が実機で成立していなかった**（#109）ので、⚠ **プロセス内の重なりは `PostingJob#claim` が塞いだ** — **ここに残るのは再起動をまたぐ重なりだけ**（記憶はプロセスと一緒に消えるので、この数え直し防止はまだ要る）
- ⚠ **ハートビートの痕跡は `tmp/run/heartbeat.json`**（`Makoto::Heartbeat`）。⚠ **監視にログを読ませない**（置き場と書式に依存させない）。⚠ **観測用の痕跡であって進行位置の状態ではない**ので、消しても再起動後の動作は変わらない
  - 🔴 **痕跡は「切り詰めて書く」のではなく「差し替える」**（2026-08-15・#81 のレビュー指摘）。⚠⚠ **`File.write` は切り詰めてから書くので、その隙に読んだ側は壊れた JSON を掴む。**⚠ **読めない痕跡は `stale?` が true になる**ので、**`makoto status` が 1 を返し、monit が正常な常駐を再起動する** — **監視のせいで監視が誤報する形**だった。⚠ **実測で 2,000 回中 625 回が nil**（#78 で投稿ごとに書くようになり、1 時間に 1 回 → ライブ当日 160 回と窓が広がった）。**同じディレクトリ内の rename は不可分なので、読む側は鍵を取らなくてよい**
  - ⚠⚠ **更新は `flock` でプロセスもまたいで直列化する。**⚠ **`Mutex` はプロセス内のスレッドしか守らない**が、**常駐は再起動で一時的に 2 本になりうる**（孤児で復旧を叩かせない理由と同じ前提）。⚠ **実測で 600 回の更新のうち 458 回が消えた**
- ⚠⚠ **止まったとみなす閾値は設定から出す**（`/scheduler/heartbeat/interval` の 3 倍、投稿の失敗は `/scheduler/posting/failure_limit`）。**間隔を延ばした瞬間に監視が誤検知しはじめる**のを防ぐ。⚠ **どちらも既定値に逃がさない**（`optional_config` を使わない）— **設定を消しただけで検知が静かに緩む形にしない**（#77 の裏返し。schema で必須にしてあるので `rake config:lint` が先に止める）
- ⚠⚠ **孤児プロセスは警告どまりで、復旧を叩かせない。**再起動の瞬間に一時的に 2 本になりうるので、ここで再起動させると**検知 → 再起動 → 検知のループ**になる。⚠ **孤児は「溜まる」のが問題**（旧実装は 11 日分溜めた）なので、即時の自動復旧より人の目が要る
- ⚠ **`/proc` が読めない環境では「孤児は無い」と答えない**（不明を返す）。**守っているつもりで無防備**になるのを防ぐ
- ⚠⚠ **孤児かどうかは cmdline の部分一致で決めない**（2026-08-15・#61）。⚠ **argv にこの文字列を含むだけの無関係なプロセスを孤児と報告する** — 踏みやすいのは**復旧のラッパースクリプト・デプロイのシェル・`pgrep` のワンライナー**で、⚠ **docs が「復旧コマンドはラッパースクリプトに逃がす」と決めている以上、この形は運用に組み込まれる。**⚠ **恒常的に踏むと本物の孤児が誤報に埋もれる**
  - **見るのは 2 つだけ**（`ProcessIdentity#script_candidates`）— ⚠ **argv の 0 番目**と、⚠⚠ **インタプリタのオプションを読み飛ばした次の 1 つ**。**位置で決め打つと `ruby --yjit bin/makoto_daemon.rb start` を取り逃がす**（#68 のレビュー指摘。⚠ **bydo の Ruby は YJIT 有効**なので実際に取りうる形）。⚠ **オプションでない要素は 1 つ目で打ち切る** — `bash -lc 'bundle exec bin/makoto_daemon.rb restart'` の第 3 要素は**スクリプトではなくシェルへの文字列**で、そこまで見ると部分一致に戻る
  - ⚠⚠ **ただし要素をそのまま突き合わせると本物を取り逃がす。**⚠ **実機の常駐は argv が `bin/makoto_daemon.rb start` という 1 要素**（bundler 経由の起動で `$0` が書き換わる。2026-08-15 に bydo の `/proc/{pid}/cmdline` を実測）。**要素の中を空白で割ってから basename を見る**
  - ⚠ **「誤報を出さない」と「本物を検知する」の両方を回帰テストに入れる**（#61 の完了条件）。**片方だけでは通ってしまう** — 実際、旧実装は前者だけ落ちる
  - 🔴 **2 つ目の要素を見るのは、先頭が Ruby のときだけ**（2026-08-18・#80 の緑 6）。⚠⚠ **これが無いと `vim app/lib/makoto/daemon/makoto_daemon.rb` を常駐と報告する**（実測）。⚠ **編集・閲覧・grep はどれも「先頭 ＋ ファイルのパス」**なので、**開発中は恒常的に踏む**
  - ⚠ **`stop` / `status` は常駐ではない**（即座に終わる）。⚠⚠ **`restart` は除かない** — **fork した子は argv を引き継ぐ**ので、**本物の常駐が `restart` のまま走っている**
- 🔴 **同じ規則で「pid ファイルの常駐」自身の身元も確かめる**（2026-08-16・#80 の黄 6）。⚠⚠ **`Ginseng::Daemon#alive?` は `Process.kill(0, pid)` しか見ない**ので、⚠ **pid が再利用されると無関係なプロセスを常駐だと答える**（実測 — `sleep 300` の pid を pid ファイルに書くと `running (PID 354866)` と表示された）
  - ⚠⚠ **孤児の側だけが argv まで見て、自分の pid ファイルは素通しだった。**⚠ **規則を `ProcessIdentity` に切り出して両方から使う**ので、**片方だけ厳しいという食い違いが起きない**
  - ⚠⚠ **倒れ方が静かなのが本題** — `run_start` が「already running」で終了し、⚠ **systemd の `Restart=always` が 5 秒ごとに叩き直す**ので、🔴 **ボットは一度も起動せず、理由もログに残らない**（warn は stderr → `bin/makoto_daemon.rb` が `/dev/null` に落とす）。⚠ **`run_restart` も `run_stop if alive?` を通って無関係なプロセスへ TERM を送る形だった**
  - ⚠⚠ **確かめられないときは「生きている」に倒す**（`/proc` の無い環境・`EACCES`・列挙してから消えたプロセス）。⚠ **呼ぶ側は既に `Process.kill(0)` で在ることを確かめている**ので、**「確かめられない」を「死んでいる」に倒すと健全な常駐の横にもう 1 本立つ**。⚠ **孤児の側が「不明」を返すのとは倒す向きが逆**（あちらは無防備を防ぐため、こちらは二重起動を防ぐため）
  - ✅ **実測（2026-08-16）** — 無関係な pid を書くと `makoto status` が `error: MakotoDaemon is not running` で **1**（＝復旧させる）を返す

#### ✅ 監視の口は HTTP で外から叩く（2026-08-16 決定・#84）

⚠⚠ **`makoto status` は箱の中からしか呼べない。**判断そのものは `Health` にあるのに、**外から確かめる手段が無かった**。⚠ **monit は fleet 全体で退役方向**で、⚠⚠ **Kuma のモニタは 99 本すべてが `http`**（push の前例はゼロ）なので、**Kuma に載せるには HTTP の口を生やすしかない。**

⚠ **これは「inbound は開けない」を緩める判断。**⚠⚠ **緩めるのは LAN 限定・読み取り専用の死活の口だけで、管理コンソールを作らないという決定は変えない。**⚠ **既定は `127.0.0.1`**（`/monitor/bind`）で、開けるのは箱ごとに `config/local.yaml` へ書く明示的な一手にしてあるので、**「開いていない」が既定のまま残る。**

- **`Makoto::MonitorApp`（Rack アプリ 1 枚）＋ `Makoto::MonitorServer`（`Puma::Server`）**。手本は tomato-shrieker
- ⚠⚠ **別プロセスにしない。**常駐の `start` / `stop` に組み込むので、**常駐が落ちれば口も閉じる。**⚠ **TCP の接続が失敗すること自体が「死んでいる」の検知**になる。⚠⚠ **別プロセスにすると、常駐が死んでいるのに口だけ生きて 200 を返す**という最悪の形が作れてしまう
- ⚠ **口が起こせなくても常駐は止めない**（ポートが埋まっている程度のことで投稿を止めるほうが害が大きい）。⚠ **黙って見逃すことにもならない** — 口が無ければ Kuma は接続に失敗して赤くなる
- ⚠ **登録のあとに開ける。**⚠⚠ **先に開けると、まだ `jobs` が 0 の `/healthz` を叩かれて赤くなる**

🔴 **口は 3 つに分ける**（`Health` の終了コードをそのまま HTTP に写すのではない）。

| 口 | 503 になる条件 | 監視の扱い |
| --- | --- | --- |
| `/healthz` | `Health#errors`（＝終了コード `1`） | **復旧させてよい** |
| `/healthz/posting` | 投稿が続けて落ちている（＝ #78 の警告） | **人が見る** |
| `/healthz/orphans` | 孤児がある／`/proc` が読めない | **人が見る** |

- ⚠⚠ **投稿の警告と孤児を同じ口に載せない。**⚠ **投稿の警告は sticky で、消えるのは「次に 1 本投稿できたとき」だけ**（→ 上記）。⚠⚠ **同じ口に載せると、赤のまま何週間も残っている間に本物の孤児が埋もれる** — **溜まっていくことの検知**（旧実装は 11 日分溜めた）がいちばん効かなくなる
- ⚠ **`/healthz` が実際に足すのは「生きているが仕事をしていない」の検知。**生死そのものは TCP の接続で分かる
- ⚠⚠ **例外は 503 に倒す。**⚠ **200 に倒すと、`Health` が落ちている間だけ監視が緑になる**（設定の欠落・閾値の不正で実際に起きうる）。**判定できないことを健全と答えない**
- ⚠ **`Health` はリクエストごとに作る**（使い回すと痕跡が変わっても古い判定を返し続け、**監視が「直ったこと」に気付けない**）
- 🔴 **答えている自分が pid ファイルの常駐かを先に確かめる**（2026-08-16・#87 のレビュー指摘）。⚠⚠ **違えば 3 つの口とも 503 にする**
  - ⚠ **「口が塞がっていても常駐を止めない」は、古い常駐がポートを掴んだまま新しい常駐がその横で動く形を許す。**⚠⚠ **そのとき Kuma に答えるのは古いほう**で、⚠ **痕跡も pid ファイルも新しいほうが書いている**ので、**3 つの口が揃って 200 を返す**
  - ⚠⚠ **孤児の口さえ緑になる** — `Health` は**自分自身（`Process.pid`）と pid ファイルの常駐**を走査から除くので、**2 本ある状態がどちらから見ても見えない**。⚠ **monit が退役していて Kuma しか見ていない**以上、これは無防備そのもの
  - ⚠ **実測（2026-08-16）** — 常駐を 2 本立てると `makoto status` は `orphan process: 912621` で `2` を返したのに、⚠⚠ **`/healthz` / `/healthz/posting` / `/healthz/orphans` は 3 つとも 200 だった**
  - ⚠ **再起動の一瞬（pid ファイルが消えている窓）も 503 になるが、これは誤報ではない** — その瞬間にこの口へ答えているのは畳まれる途中の常駐
- ⚠⚠ **正常な応答をログに書かない。**Kuma は 1 分ごとに叩くので、⚠ **書くと 1 日 4,000 行を超えて平常日のログが監視で埋まる**（黄 9 の裏返し）
- ⚠ **設定は `optional_config` で読まない**（`enabled` / `bind` / `port` を schema で必須にする）。**設定を消しただけで監視の口が静かに閉じる形にしない**（#77 の裏返し）
- **ポートは `4567`**（tomato-shrieker と同じ）。⚠ **本番は非同居なので衝突しない**（→ 上記「稼働先は旧サーバー非依存」）。Kuma への登録を他の ginseng 系ボットと同じ形にしておく
- ⚠ **「どの枠が落ちたか」を枠ごとに見るのは `0.6` へ送った**（→ #86。⚠ **2026-08-19 に `0.3` → `0.4`、2026-08-22 に `0.4` → `0.6`**）。⚠⚠ **`Heartbeat` は `failures` を全体で 1 つしか持たない**ので、枠別にするとデータ構造から変わる（#78 を入れた直後にそこを作り直さない）

### 投稿の欠落は詰めない。進行位置は状態ではなく計算で出す（2026-08-02 決定・#10）

**失敗した投稿は、欠落したまま次の枠へ進む。**⚠ **落とした分を後ろに詰めない。****旧実装でも同じ判断をした前例がある。**

- ⚠⚠ **詰めようとすると「いま何番目か」を状態として持つことになり、再起動後の復帰が計算で出せなくなる。**「プロセスの寿命を設計に含める」（上記）と正面から衝突する
- **進行位置は時刻から導出する**（`Makoto::Timetable#index_at`）。⚠ **落ちて戻ってきても位置がずれない**
- ライブは 8 時間で 240 枠あるので、1〜2 本落ちても実害が小さい

⚠ **したがって「投稿が出たかどうか」を記録する必要があるのは、重複回避（#11 / #13）のためであって、進行の再開のためではない。**この 2 つを混同しない。

### 原稿の上書きは「具体的なものが勝つ」5 段（2026-08-05 決定・#12）

**特定の日は、前もって用意した原稿で自動生成を上書きする。**旧実装の 3 段構え（特定日 → 季節 → 無指定）に 2 段足して、`Makoto::MessageSelector` に落とした。

| 段 | 引くもの | 旧データでの中身 |
| --- | --- | --- |
| 1 | **その年のその日**（`message.year` 一致） | 無し。⚠ **台本（#13 / #14）がここに入る** |
| 2 | **毎年のその日**（`year` が NULL） | `holiday` 6 件（元日・プリキュアの日・バレンタイン・エイプリルフール・キュアスタ！の誕生日・クリスマスイブ） |
| 3 | **記念日**（`/message/anniversary`） | `birthday` 19 件（11/4） |
| 4 | **季節**（`message_season` の月一致） | `morning` 82 件 |
| 5 | **無指定**（通年） | `morning` 155 件 |

- ⚠ **`year` 列は #12 で足した**（migration 003）。⚠ **NULL は「毎年」**。旧データ 388 件はすべて NULL
- ⚠⚠ **記念日として登録した type は、その日以外では選ばれない。**除かないと、日付を持たない `birthday` 19 件が段 5 に混ざって**毎朝バースデーの原稿が出る**
- ⚠ **使ってよい `type` は呼ぶ側が許可リストで決める。**朝挨拶（#17）は `holiday` / `birthday` / `morning`、ライブ（#13）は台本の type だけ。⚠ **許可リストに無い type は日付が一致しても選ばれない**ので、ライブの台本を朝挨拶が横取りしない
- ⚠⚠ **`template` 109 件と `calling` 13 件を許可リストに入れない**（全件が `%s` を含む。→ 上記コーパスの節）
- **原稿が無ければ nil を返す**＝通常の生成にフォールバックする合図。例外にしない
- **原稿の追加・削除・下見は CLI から行う**（`makoto message add` / `list` / `preview` / `remove`）。⚠ **コード変更なしで原稿を足せること**が #12 の完了条件

### 予告の日付は枠ではなく原稿が持つ（2026-08-08 決定・#14）

**11/1 からの予告は、「11/1〜11/3 に動く枠」ではなく「毎日ある枠 ＋ その日の原稿」で作る**（`Makoto::Announcement`）。

- ⚠⚠ **枠は日付を知らない。**枠は毎日 1 本あり、**その日の原稿が無ければ `MessageSelector` が nil を返して何も投稿しない**（→ 上記「原稿の上書き」）。⚠ **予告を止めるのも動かすのも原稿の側**なので、機能のフラグを持たない
- ⚠ **日付を動かすのにコード変更もデプロイも要らない**（`makoto message add --date=2026-11-01`）。#12 の完了条件がそのまま効いている
- ⚠⚠ **予告の type は `/message/anniversary` にも登録する。**登録が無いと日付を持たない予告の原稿が段 5（無指定）に混ざって**毎日予告が出る**。⚠ **`Announcement` はこの登録が無ければ起動時に落ちる**（黙って毎日出るより早く気付ける）

- **常駐が投稿を並べる場所は `MakotoDaemon#register_jobs`。**⚠ **投稿の中身はそこに書かない**（各機能が自分の `PostingJob` を持つ）

### ライブの並びは抽選ではなく整列（2026-08-13 決定・#13）

**バースデーライブ（`Makoto::Live`）は枠を 4 つ持つ。**開始告知で始まり、8 時間の進行を挟んで、終了告知で終わる。⚠ **前日（11/3）の増量は別の枠**（→ 上記「枠は 1 日 1 本」）。

| 枠 | 時刻 | 中身 |
| --- | --- | --- |
| `live-eve` | 11/3 12:00〜20:00（1h） | 前日の増量。助走をつける |
| `live-open` | 12:00 | 開始告知。⚠⚠ **ミュート導線をここに書く**（#13 の完了条件・参加は任意） |
| `live` | 12:02〜20:00（3m・160 枠） | 曲・カバー・MC（`Setlist` / `LiveProgram`） |
| `live-close` | 20:00 | 終了告知 |

- ⚠⚠ **セットリストは抽選ではなく整列**（`Setlist`）。日常の曲紹介（#16）が使う `TrackLottery` とは別軸で、**`kind` の重み付けも一様抽選も使わない**。⚠ **同じ日付・同じ枠数なら何度組んでも同じ並びになること**が前提（→ 上記「進行位置は状態ではなく計算で出す」）
- ⚠⚠ **発売日で並べるだけで、キュアソード関連 11 曲が 41〜56%＝中間点をまたぐ位置に固まる**（実測・2026-08-13）。元ネタの「昼の部の締めから夜の部の前半にかけて集中」が、**特別扱いを 1 つも書かずに再現される。**⚠ **だから前後編の蝶番は曲名ではなく位置で決めてよい**（→ [birthday-live.md](birthday-live.md)）
- ⚠ **アンカーの 2 曲だけは曲名で指す**（`/live/setlist/opening` = 〜SONGBIRD〜 ・`closing` = こころをこめて）。⚠ **置く位置は 3 つ**（`opening` は頭と蝶番の 2 回歌う）。⚠⚠ **曲名の数（2）と枠の数（3）を混ぜない**。⚠⚠ **引けなければ黙って別の曲を置かず、その位置を諦める**（並びは崩さない）
- ⚠⚠ **曲は原稿ではないので「原稿が無ければ黙る」が効かない。**告知や MC は `MessageSelector` が nil を返して止まるが、**進行の枠を素通しにすると毎日 12:02〜20:00 に 8 時間ぶんの曲が流れる。**⚠ **ライブ当日かは `/message/anniversary`（開始告知の type の登録日）で判定する**（`LiveProgram#live_day?`）。⚠ 日付の正本を 2 箇所に割らない

  - ⚠⚠ **写しを使い始めたら、その process では引き直さない。****ライブの最中に cure-api が復活して並びが変わるほうが困る**

  - **cure-api が引けない / 1 件も一致しない / 要求数に満たない**の 3 つを別々の警告にする

### リリースフロー

1. `develop` で開発・コミット
2. リリース時に `develop` → `main` へ PR を作成しマージ
3. `main` でタグを打ちリリース

⚠ **`develop` 宛の PR では `Closes #n` が効かない。**GitHub は**既定ブランチ（`main`）へのマージでしか Issue を自動クローズしない**ので、develop へのマージでは Issue が open のまま残る（2026-08-05 に #43 / #12 で確認）。**書いてもよいが、閉じるかどうかは必ず手で判断する**（ラップアップの分類ルールは下記「Issue / マイルストーン運用」）。

⚠ **`gh pr create` では `--base develop` を必ず指定する。** 省略するとリポジトリ default の `main` が base になり、未リリースの変更が黙って main に乗る（モロヘイヤで 3 件同時に踏んだ事故がある）。リリース PR のときだけ `--base main`。作成直後に `gh pr view <番号> --json baseRefName` で確認する。

## Issue / マイルストーン運用

- **Issue 駆動**。思いつきの改善は直接コミットせず、まず Issue 化する

  ```bash
  gh api repos/pooza/makoto2/milestones -f title='0.3' -f state='open' -f description='...'
  gh issue edit <n> --milestone '0.3'

- 🔴 **マイルストーンの名前に末尾の `.0` を付けない**（2026-08-16 決定。`0.2.0` → **`0.2`**）
  - ⚠⚠ **マイルストーンは版そのものではなく「その版の系列」の箱。**⚠ **1 つの箱の中で複数のリリースを出す** — `0.2` からは **v0.2.0 / v0.2.1** が出ている
  - ⚠ **`0.2.0` という名前だと、v0.2.1 が別の箱の話に見える。**⚠⚠ **実際にそう読めてしまう形だった**（マイルストーンの表に `0.2.1` の行が並んでいた）
  - ⚠ **リリースのタグは従来どおり 3 桁**（`v0.2.1`）。**箱の名前だけを 2 桁にする**

- 🔴 **日付でしか閉じられないものを、開発のマイルストーンに入れない**（2026-08-16 決定）。**専用の箱へ隔離する**（いまは **`live-2026`**）
  - ⚠⚠ **「開発の完了」と「当日の観測」は別種の仕事。**同じ箱に入れると**開発の進行が暦に縛られる** — ⚠ **実際に `0.2` が 11 月まで閉じられず、次の開発に進めない形になっていた**
  - ⚠ **開発側の完了条件は「本番へ投入した」まで。**「本番で実際に出た」は隔離した箱の側で見る
  - ⚠⚠ **これは「本番で動いたことを確かめない」という意味ではない。**⚠ **確認そのものは `live-2026` の Issue に**、**当日のチェックリストの形で**残す（→ #85）。**むしろそのほうが当日に使える**

- **サイズラベルと重み予算**で管理する（件数では実態を反映しないため）

  | ラベル | 想定差分 | 重み |
  | --- | --- | --- |
  | `size:S` | 50 行未満 / 単発修正・docs | 1 |
  | `size:M` | 50〜200 行 / 新メソッド・契約変更 | 3 |
  | `size:L` | 200 行超 / 新機能・スキーマ変更・複数ファイル横断 | 8 |

  1 マイルストーンの目安は **20〜25 重み**。超えそうな Issue は次のバージョンへ送る。計画書は作らず、Issue ＋ マイルストーン ＋ 重み合計で管理する

  🔴 **逆に、暦に縛られていない箱で目安を破らない**（2026-08-22）。⚠⚠ **`0.4` は「`0.3` 以降ぜんぶ」の仮の箱として重み 41 まで膨れていた** — ⚠ **「11/4 に要るか」で振り分けた残りが溜まる場所**になっていて、**版として何を出すのかが誰にも言えない状態だった。**⚠ **軸を「何を出す版か」に戻して 3 つに割った**（→ 下記のマイルストーン表）。
- **新しいマイルストーンに着手したら最初にバージョンをバンプする**（開発中バージョンを常に識別可能にする。実行中のコードが判別できないとデプロイ・検証で事故る）

- **マイルストーン未設定の軽い課題は近接処理する**（重い作業の合間に片付ける）。ただし大きな設計案件はその場の雑談処理に混ぜない

## CI（2026-07-30 決定・#6）

GitHub Actions で **`rubocop` / `rake config:lint` / `rake test`** を回す（[.github/workflows/test.yml](../.github/workflows/test.yml)）。`develop` / `main` / `feature/**` への push と、`develop` / `main` 宛の PR が対象。

- **CI に秘密情報を持たせない。** `config/local_sample.yaml` をそのままコピーして使う。**テストは WebMock で通信を遮断してある**ので、CI から実サーバーへは 1 通も飛ばない（→ コーディング規約の WebMock の項）
- `rake migration:run` も流す。マイグレーションが 0 本の間も正常終了する
- ⚠ **CI があってもローカル実行を省略しない。** 「CI が見るから」でローカルの lint / test を飛ばさない（規約どおり）
- **Dependabot**（[.github/dependabot.yml](../.github/dependabot.yml)）は **`open-pull-requests-limit: 0`**。バージョン更新の PR は止め、**セキュリティ更新の PR だけ受ける**（別枠なので届く）。締め切りまでは更新 PR のノイズを避ける。モロヘイヤと同じ方針。脆弱性アラート自体はリポジトリ設定側で有効
- ⚠⚠ **Dependabot のアラートは `develop` に修正が入っても閉じない。**⚠ **GitHub が見るのは既定ブランチ（`main`）**なので、**`develop` → `main` のリリースまで open のまま残る**（`develop` 宛の PR で `Closes` が効かないのと同じ理屈 → 上記「リリースフロー」）。⚠ **「直したのに open」を未対応と読み違えない。**実例: `json` の低リスク 1 件は **2026-08-09 に `Gemfile.lock` が 2.21.2（修正版）になったのに、`main` が v0.1.0 のままだったので open で残っていた**。✅ **v0.2.0 が `main` に入って閉じた**（2026-08-16 時点で open のアラートは 0 件）
- ⚠⚠ **fork から来た PR では CI が自動で走らない。**このリポジトリは public なので**外部からの PR が届きうる**（実例: #56・`shin4141`・2026-08-14）。⚠ **workflow の実行には手動承認が要る**ので、**チェックが空なのを「CI が緑」と読み違えない。**⚠ **承認する前に差分を読む**（承認＝自分のリポジトリの CI で他人のコードを走らせること）。⚠⚠ **承認は run 単位なので、コミットを積まれるたびに要る** — #56 は 2 コミットとも `action_required` で溜まっていた。**古いほうは承認せず、最新の head だけ承認して緑を確認し、squash merge した**（2026-08-15）

- **ログは syslog に出る**（ident は `makoto2`。`journalctl -t makoto2`）。ginseng の Logger が JSON 1 行で吐く
- 🔴 **「平常日のログ」と「壊れた日のログ」が同じにならないようにする**（2026-08-16・#80 の黄 9）。⚠ **ライブの 4 枠は毎日空回りする設計**なので `no text` が毎日出ており、⚠⚠ **11/4 に 160 枠が全滅しても平常日と 1 文字も変わらなかった**（実測 1 日 171 行）
  - ⚠ **枠が黙ったこと自体は `debug` に落とす**（`/logger/level` = `info` なので既定では出ない）。**空回りは異常ではない**（→ 上記「原稿の上書き」）
  - ⚠⚠ **「出るべき日に出なかった」は中身を知っている側が言う** — **`LiveProgram#call` がライブ当日の枠で本文を作れなければ `warn`**。⚠ **そこまで来ているということは「ライブ当日で、枠の中」**なので、**本文が無いのは原稿が無いのではなく壊れている**
  - ⚠ **例外にはしない**（1 枠の異常で残りの 8 時間を落とさない）
  - ⚠ **枠ごとの空回りを追いたいときは `/logger/level` を `debug` に下げる**
- 🔴 **`logger.warn` は出口の scrub / マスクを通っていなかった**（2026-08-16・#97）。⚠⚠ **上流（`Ginseng::Logger`）が上書きしているのは `info` と `error` の 2 つだけ**で、⚠ **残りは `Syslog::Logger` の実装がそのまま走る** — **実測で `token` が平文で出た**。⚠ **`Makoto::Logger` で `warn` / `debug` / `fatal` も出口に通した**（「出口 1 つに置けば渡し方の規約を覚えなくてよい」という #82 の前提が、`warn` では成立していなかった）
- **`/logger/mask_fields` が秘密情報の唯一の正本。** ログのマスクと `makoto config` の伏せ字が同じリストを見る。⚠ このリストは fail-open な rescue の内側で読まないこと（読めなければ「マスク対象ゼロ ＝ 素通し」になる）
- **`bin/makoto_daemon.rb` が標準出入力を `/dev/null` に落とすのは `start` / `restart` のときだけ。** 常駐時の `Errno::EPIPE` は避けつつ、`stop` / `status` の出力は監視やスクリプトから読めるようにしてある
- **スケジューラはハートビートを 1 本持つ**（`/scheduler/heartbeat/interval`）。登録した投稿の数を一緒に出すので、「常駐しているが何もしていない」状態が検知できる
- ⚠⚠ **枠ごとにジョブを登録しない。**ライブは 8 時間で 240 枠あり、枠の数だけ登録すると日をまたぐたびに登録し直すことになる（＝進行位置を状態として持つのと同じ）。**`/scheduler/tick` の間隔で叩き、そのつど「いま枠の頭か」を時刻から計算する。**⚠ **枠の間隔は tick より長いこと**（短いと 1 回の叩きが複数の枠に跨がって取りこぼす。`PostingJob` が起動時に弾く）
- ⚠⚠ **枠の頭を拾う幅は tick と別に持つ**（`/scheduler/tolerance` = 30s・2026-08-16・#90）。⚠ **同値だと拾えるのは tick が `[枠の頭, 枠の頭+tick)` に落ちたときだけで、余裕が構造的にゼロ**になる。⚠⚠ **ライブの枠間隔 180 秒は tick の 10 秒の整数倍なので、位相ずれは 160 枠すべてに同じように効く**（1 枠だけの事故にならない）。⚠ **広げても二重投稿にならない**（同じ枠は 1 回しか処理しない → `PostingJob#claim`）。🔴 **以前はここを冪等キーに任せていたが、実機で成立していなかった**（#109・下記）
- ⚠⚠ **HTTP のタイムアウトは `Makoto::HTTP` の側で渡す**（#90）。⚠ **`Ginseng::HTTP` が HTTParty に `timeout:` を渡すのは `upload` だけ**で、⚠⚠ **`get` / `post` の実効は Net::HTTP 既定の 60 秒**だった。**再送 3 回と合わせて 1 本の投稿が最悪 182 秒 ＝ ライブの枠間隔とほぼ同じ**。⚠ **上流にも起票した**（`pooza/ginseng-core#514`）が、⚠⚠ **利用者が 2 つになった**（→ #37）ので**先に自分の箱で塞ぐ**
- ⚠ **投稿の冪等キーは枠の頭の時刻から作る**（`{名前}-{枠の時刻 UTC}`）。⚠⚠ **同じ枠なら本文が変わっても同じキー**（抽選をやり直してもキーが動かない）
- 🔴 **「Mastodon 側が畳む」を当てにしない**（2026-08-19・#109）。⚠⚠ **実機は同じキーの 2 通目を畳まず 500 を返した**（`bydo` → `st2`・6 枠すべて）。⚠ **素の POST では逆に畳まれず別々の status ができる**という、噛み合わない 2 つの観測がある（応答ボディは `Ginseng::GatewayError` が捨てるので読めない → #101）。🔴 **プロセス内の重なりは `PostingJob#claim` が塞ぐ** — **「その枠は処理した」をプロセス内だけ覚える。**⚠ **キーに残っている仕事は再起動をまたぐ重なりだけ**（最後の砦としては残す）
- ⚠⚠ **常駐の開始直後に 1 回叩く**（`Scheduler#schedule_posts`・2026-08-08・#47）。`every` は最初の間隔を待つので、これが無いと**枠の頭 ＋ tolerance の内側で再起動した枠が落ちる**。⚠ **位置の計算は正しいのに、再起動直後にそれを呼ぶ機会が無い**という形で「落ちて戻ってきても位置がずれない」が最後の 1 行で効いていなかった。⚠ **投稿済みの枠をもう一度処理しても 1 通で済む**（`PostingJob#claim` が同じ枠を二度叩かない → #109）ので、叩いて困る経路は無い
- ⚠⚠ **繰り返しの登録が先、初回の tick が後。**初回の tick は投稿を伴うので **HTTP の再送で秒単位に伸びうる**。⚠ **逆順にすると、伸びている間に次の枠が tolerance ごと過ぎて落ちる**（ライブの枠は 2 分間隔）
- ⚠ **`bin/makoto_daemon.rb start` は前景で走る。**背景化するのは `restart`（`fork` ＋ `setsid` ＋ `detach`）。**デプロイ・監視から起動するときは `restart` を使う**（→ #15）

## コーディング規約

### Ruby（RuboCop）

モロヘイヤ・tomato-shrieker と同じ方針を引き継ぐ。

- **`Layout/EndAlignment: EnforcedStyleAlignWith: variable`** — 見栄えのための位置揃えを自動検出する（下記のインデント方針）
- **`Style/RedundantReturn: Enabled: false`** — 暗黙の return を使わない方針と衝突するため無効化する
- 収集スクリプト（[seed/](../seed/)）は Python のまま残してよい。RuboCop の対象外

言語に依存しない規約:

- **インデントは常に論理的な 2 スペース。** 見栄えのための位置揃え（代入の右辺に制御式を置いて深くインデントする等）は使わない。インデントの深さはコードの論理構造だけを反映する
- **暗黙の return を使わない**（Ruby を選ぶ場合、メソッド末尾でも `return` を省略しない）
- **lint / test を「環境が壊れている」で迂回しない。** 依存導入・環境修復をしてから必ず実行する。「CI が見るから」でローカル実行を省略しない
- **機能追加・バグ修正には対応するテストを書く**（CI で実行可能な範囲で。外部 API 依存のテストは無理に書かなくてよい）
- ⚠ **WebMock は `require` だけでは有効にならない。`WebMock.enable!` を呼ぶまで、`stub_request` も `disable_net_connect!` も無言で素通りする。** MAKOTO は投稿するボットなので、これを忘れるとテストが**実サーバーに書き込む**（2026-07-30 に実際にステージングへ 10 通投げた）。`TestCase#setup` で有効化し、**「stub していないリクエストが `WebMock::NetConnectNotAllowedError` になる」こと自体をテストする**
- ⚠ **再送する経路で外部へ書き込むときは冪等キーを持つ。** MAKOTO は無人で投稿し続けるので、`HTTP#retryable?` の再送は「投稿が二重に出る」経路でもある（Mastodon が受理した後に応答だけ失われると、再送が同じ投稿をもう 1 つ作る）。1 回の論理的な投稿につき `Idempotency-Key` を 1 つ作り、**全試行で使い回す**。テストは「キーが付いている」ではなく**「同じキーが全試行で飛ぶ」**ことを見る（前者では 3 通投稿される事故を検知できない）
- **運用上必須の設定は JSON Schema の `required` に入れる。** 親キーだけを `required` にしても、中身が欠けた設定は `rake config:lint` を通り抜け、その設定を使う瞬間に初めて落ちる
- ⚠⚠ **URL は `format: uri` ではなく `pattern: '^https?://'` で要求する**（2026-08-18・#35）。⚠ **`Ginseng::Config#errors` は `validate_formats` を渡していない**うえ、⚠⚠ **渡しても json-schema の `uri` は RFC 3986 の相対参照を許すので `これはURLではない` すら通る**（実測。弾けるのは `::::` のような構文破綻だけ）
  - 🔴 **`format: uri` が書いてあることで守られているように見えるのが、いちばん困る形**（→ 下記「fail-open な `rescue` の内側で設定値を読まない」と同じ「守っているつもりで無防備」）。⚠ **`mastodon.url` の `htps://` は投稿しようとした瞬間まで分からなかった**
  - ⚠ **`pattern` は「`http(s)` で始まるか」しか見ない。**「URL として妥当」を保証していると読まないこと（狙いは typo を弾くこと）
  - ⚠⚠ **根は `ginseng-core` の共通コードなので、症状は利用アプリ 2 つに出ている**（`pooza/ginseng-core#516` ／ 同じ穴が `pooza/tomato-shrieker#1461`）。⚠ **`pooza/ginseng-core#514` と同じく先に自分の箱を塞いだ**（→ #37）。**上流が format を実効化する側に倒しても `pattern` は冗長になるだけなので消さない**
- ⚠⚠ **省略できる設定は `optional_config` で読む。素の `config[]` を使わない**（2026-08-15・#77）。⚠ **`Ginseng::Config#[]` はキーが無ければ例外を上げる**（既定値へのフォールバックが無い）ので、**「設定を消せば止まる」と説明した設定を素で読むと、消した瞬間に落ちる**
  - ⚠⚠ **`rake config:lint` は通る**（schema が必須にしていないため）。**使う瞬間まで分からない**
  - ⚠ **落ち方が 2 通りに分かれるのが厄介** — **起動時に読むもの**（`/live/hashtag`）は常駐が起動せず監視が拾えるが、⚠⚠ **枠の中で読むものは `PostingJob` の rescue に飲まれ、「登録ジョブ 5 で健全」のまま 160 枠が沈黙する**
  - ⚠ **`rescue` で受けない。**キーの有無だけを見て、⚠⚠ **値を読む側の失敗は握り潰さない**（`rescue` にすると設定パスの typo が同じ穴に落ちる → 上記「fail-open な rescue の内側で設定値を読まない」）
  - ⚠ **テストは「キーはあるが空」ではなく、本物の「無い」を見る**（`test/optional_config.rb`）。⚠⚠ **旧 `test_excludes_nothing_without_the_setting` は名前に反して空配列しか見ておらず、素通ししていた**
- **fail-open な `rescue` の内側で設定値を読まない。** 設定パスの typo が例外として飲まれ、ガードが恒常 no-op になる（モロヘイヤで実際に踏んだ「守っているつもりで無防備」という静かな穴）。ガードのパラメータは定数化するか rescue の外で評価し、**「実際にブロックする」正テストを必ず書く**
- ⚠ **例外メッセージを埋め込むときは `error_message` を通す。** Sequel / SQLite の例外は **ASCII-8BIT** で上がるので、台詞のような非 ASCII を含む SQL が失敗すると `"...: #{e.message}"` が `Encoding::CompatibilityError` になる。**エラー処理そのものが落ちて本当のエラーが隠れる**（無人で動くボットでは誰も気付けない）
  - ⚠⚠ **ログの側は覚えなくてよい。**`Makoto::Logger#create_message` が**出口 1 つで scrub する**ので、`logger.error(error: e)` はどこから呼んでも安全（2026-08-15・#79）。⚠ **`error_message` は「例外を文字列に埋める」ため、こちらは「ログに出す」ため**で経路が違う（`raise "...: #{error_message(e)}"` はログを通らない）
  - 🔴 **直す場所を「呼び出し側 6 箇所」にしなかった理由** — ⚠ **7 箇所目が生えた瞬間に破れる**うえ、⚠⚠ **破れても静かに壊れる**（テストが落ちるのは、その新しい呼び出しに不正なバイト列が来たときだけ）。**規約で守るより、通り道を 1 つにする**
  - ⚠⚠ **キーも見ること。**値だけ直すと、**壊れたキーを持つ Hash がそのまま出口を抜け、syslog の `String#strip` で落ちる**。⚠ **`to_json` は不正なバイト列をそのまま通す**ので、そこでは止まらない（⚠ **`symbolize_keys` 自体は落ちない** — ActiveSupport が `key.to_sym rescue key` で握る）
  - 🔴 **秘密は出口でもう一度落とすこと**（`Logger#drop_secrets`）。⚠⚠ **`Ginseng::Logger#create_message` は内部で例外を握ると、渡された Hash をマスクを通さずにそのまま返す** — ⚠ **実際に踏むのは `backtrace` を持たない例外**（`raise` していない例外を `error:` に渡した形）。⚠⚠ **しかも #79 の scrub がこれを悪化させた** — **修正前は syslog で落ちて「ログごと消えて」いたものが、出力できるようになった結果、秘密がそのまま書かれる。「ログが消える」を「秘密が漏れる」に変えていた**（2026-08-15 実測・#82 のレビュー指摘）。⚠ **安全網を足すときは「何が出せるようになったか」を数える**
  - ⚠ **マスクの設定が無いときは既定のリストへ倒す。**⚠⚠ **マスクしない方向へは倒さない**（設定の不備で秘密が平文に戻るほうが事故が大きい）
  - ⚠ **「不正なバイト列の Symbol は作れない」で済ませない**（2026-08-15 に一度これで落ち残した）。**`String#to_sym` が `EncodingError` を上げるのは不正なバイト列のときだけ**で、⚠⚠ **Windows-31J のように「別の符号化として妥当」な文字列は、その符号化を持ったまま Symbol になれる**
  - ⚠ **踏むのは「壊れた／切り詰められたバイト列」**（`Net::HTTPBadResponse` の `wrong status line: "..."` など）。**ASCII-8BIT でも中身が妥当な UTF-8 なら落ちない**ので、Sequel の例外では踏まない。⚠⚠ **確率は低いが、踏むと `logger.error` 自身が再送出し、`Scheduler#tick` の rescue も貫通して stderr へ抜け、`bin/makoto_daemon.rb` が `/dev/null` に落とすので 1 行も残らなかった**
  - ⚠ **いま入っている ginseng-core（1.15.28）の `mask` はキー名でしか落とせない。**⚠⚠ **値の文字列に埋まったトークン（`url: "...?access_token=xxx"`）は素通りする**（上流の新しい版には `mask_url` がある）。**MAKOTO は Bearer ヘッダで投げ、cure-api の URL にも秘密が無い**ので、いまは踏まない
- ⚠ **テストの共通処理は `setup` メソッドではなくコールバック（`setup do ... end`）で登録する。** メソッドにすると、サブクラスが `setup` を定義して `super` を忘れた瞬間に外れる。**忘れても落ちない**ので素通しに気付けない（WebMock の通信遮断で実際に起きうる形だった）
- **秘密情報はログに出さない。** OAuth 認可コード・アクセストークン・API キーは scrub 対象に入れる

    for m in 0.4 0.5 0.6 live-2026 1.0; do
      gh issue list --repo pooza/makoto2 --state all --milestone "$m" \
        --limit 100 --json number,labels > "/tmp/ms-$m.json" || exit 1

      jq -r '[.[] | (.labels|map(.name))
        | (if index("size:L") then 8 elif index("size:M") then 3
           elif index("size:S") then 1 else 0 end)]
        | "件数=\(length) 重み=\(add // 0)"' "/tmp/ms-$m.json"
    done
    ```

## LLM プロバイダとモデル（2026-07-30 決定・#3）

**Anthropic Claude / `claude-opus-5`。全機能で同じモデルを使う。**

- **公式の Ruby SDK がある**（`gem install anthropic` → `Anthropic::Client.new`）。Messages API・ストリーミング・プロンプトキャッシュ・ツール呼び出しが揃っており、「LLM だから Python」はクライアント層では成り立たない
- **機能ごとにモデルを変えない。** キャラの一貫性が第一の評価軸である以上、語り口の基準を 2 つ持つのは目的に逆行する。コスト最適化は必要になってから

### コーパスはプロンプトに全部載る（実測）

**応答に使える台詞 561 件で 6,969 文字**（平均 12 文字・最長 70 文字）。`quote` 956 件と `message` 388 件を合わせても 3 万文字弱で、**コーパス全体がシステムプロンプトに収まる**。

### 実装上の要点

- **プロンプトキャッシュを使う。** コーパスをシステムプロンプトの先頭に固定し、末尾のブロックに `cache_control` を置く。ライブ当日は 2〜3 分間隔で投稿するので **1 時間 TTL** が効く（8 時間 194 曲で概算 $10 → $3）
- ⚠ **Ruby SDK は `system_:`（末尾アンダースコア）** — `Kernel#system` との衝突を避けるため。`system:` ではない
- ⚠ **レスポンスの `.type` は Symbol**（`:text` であって `"text"` ではない）
- ⚠ **`stop_reason` が `:refusal` のことがある。`content` を読む前に必ず分岐する。** 安全性の分類器が働くと HTTP 200 で本文が空になるので、`content[0]` を無条件に読むコードは壊れる。**MAKOTO は無人で投稿し続けるので、拒否されたら定型文にフォールバックして黙って落ちないようにする**
- サーバー側フォールバック（`fallbacks: "default"`）を既定で有効にする
- **API キーは `config/local.yaml`（gitignore）に置き、ログの scrub 対象に入れる**

### ⚠ Claude Max の契約枠では API は使えない

**Max プランは claude.ai / Claude Code / デスクトップアプリ向けで、API 利用は含まれない。** MAKOTO が API を叩く分は Developer Platform 側の従量課金になる（別勘定）。「Max が余っているからその枠で」は成立しないので、API クレジットを別に用意する。

そのうえで、**実行時に LLM を呼ぶ範囲を絞れば従量課金はかなり小さくできる**。

| 機能 | 実行時に LLM を呼ぶか |
| --- | --- |
| 朝挨拶 | **原則ノー。** 前もって用意した原稿を配信する（#12 の上書き機構）。素材は `morning` 237 件 |
| バースデーライブの告知・進行 | **ノー。** 台本は前もって書く。11/1 の予告も同じ |
| 曲紹介 | 紹介文テンプレート ＋ 曲データで足りるなら不要。語り口に幅が欲しいところだけ呼ぶ |
| チャットボット | **イエス。** ここだけは実行時に必要 |

原稿・台本の執筆そのものは **Max の枠内で対話的にやればよい**（Claude Code や claude.ai で書いて `message` に流し込む）。**API 課金が必要なのは実質チャットボットだけ**になる。

### 予算の目安は月 $10（利用状況で見直す）

原稿方式に寄せた結果、**定時投稿の課金はほぼゼロになり、この枠はまるごとチャットボットに使える**。ハードリミットではなく、**運用しながら見直す前提の目安**。

前提: システムプロンプトに台詞 561 件を同梱すると概算 12,000 トークン。Opus 5 は入力 $5 / 出力 $25 per MTok。

| 条件 | 1 応答あたり | 月 $10 で |
| --- | --- | --- |
| キャッシュ無し・561 件同梱 | 約 $0.065 | 約 150 回（1 日 5 回） |
| キャッシュ読み・561 件同梱 | 約 $0.011 | 約 900 回（1 日 30 回） |
| キャッシュ無し・150 件に絞る | 約 $0.020 | 約 500 回（1 日 16 回） |

⚠ **プロンプトキャッシュはチャットボットではライブほど効かない。** メンションが散発的だと 5 分 TTL が切れ、毎回キャッシュ書き込み（1.25 倍）が乗って**かえって高くつく**。効くのは会話がバースト的に来るときだけで、定時投稿とは前提が違う。

**歯止めは 3 つ用意する。**

1. **同梱する台詞を絞る** — 効果が一番大きい。`form` と `priority`（1〜5 に分布）で選抜する。**何件同梱すれば語り口が保てるかは #19 で実測して決める**
2. **1 日あたりの応答回数に上限を持つ**（コード側・#18）
3. **Console 側に支出上限を設定する**（運用側）

### LLM が落ちてもライブは走る

**8 時間の枠は LLM の可用性に依存させない。** 生成に失敗したら台詞コーパスから定型で投げるフォールバックを最初から用意する（→ #10 / #13）。

## データストア（2026-07-30 決定・#4）

**SQLite ＋ Sequel。**

旧実装は PostgreSQL で `ginseng-postgres`（pg + Sequel）も手元にあるが、**保持するデータが小さく、常駐プロセスを増やしたくない**ため採らない。

| データ | 量 | 性質 |
| --- | --- | --- |
| 台詞コーパス | 1,340 行 | 更新は稀・読み取り専用に近い |
| 曲 | 4,305 行 | 同上 |
| 投稿履歴 | 増え続ける | 重複回避のための書き込み |

- **常駐プロセス 1 本という決定と整合する。** PostgreSQL を建てると監視対象と「ライブ 8 時間の間に落ち得るもの」がもう 1 つ増える
- **Sequel を挟むので、後から PostgreSQL へ移せる**（`ginseng-postgres` も Sequel ベース）
- 2GB CT に対して圧倒的に軽い

### ⚠ バックアップは `VACUUM INTO` で取る

**稼働中の SQLite ファイルを生でコピーすると壊れた写しになる。** `writersbase-tools` の `google_drive_backup` は `rclone sync` でパスを生コピーするため、そのままでは使えない（chubo2 が Uptime Kuma で同じ判断をしている）。**`VACUUM INTO` で一貫スナップショットを作ってから上げる。**

コーパスは唯一の代替不能な資産なので、バックアップ手順は #8 の完了条件に含める。
