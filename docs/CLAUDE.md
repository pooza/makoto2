# makoto2 開発ガイド

このファイルがプロジェクトのルール・構造・履歴の**正本**。メモリ（`MEMORY.md`）はポインタと補足だけを持つ。

## プロジェクト概要

**MAKOTO** は、剣崎真琴（キュアソード / CV: 宮本佳那子）をモデルにした AI マスコットボット。Mastodon サーバー「キュアスタ！」（precure.ml）で稼働する。

- **アカウントは継続使用**: [@makoto](https://precure.ml/@makoto)（44,161 投稿・最終投稿 2026-06-24）
- **コードは作り直し**: 旧実装 [pooza/makoto](https://github.com/pooza/makoto)（最終コミット 2024-11-10）はアーカイブ済み。**使い回さない**
- **言語・スタックは自由**（Ruby 縛りなし）。未決＝下記「未決事項」
- **稼働先は旧サーバー（lbock）非依存**。専用 CT（2GB）に隔離して建てる。旧実装は本番サーバー（lbock）に同居して孤児プロセスを撒いた前科があるため、同居させない。**開発環境の CT は 2026-07-30 に用意済み（`bydo`）**、本番の置き場は未決（→ 下記「実行環境」）
- モロヘイヤ（[pooza/mulukhiya-toot-proxy](https://github.com/pooza/mulukhiya-toot-proxy)）の webhook 出力を受ける構成を想定する

**ハドラーブロス**（[@hadlarbot](https://mstdn.delmulin.com/@hadlarbot)・895 投稿・最終 2025-01-06）は **makoto2 のスコープ外**。要件が MAKOTO とまったく異なり、**必要なのはチャットボットの部分だけで、急いでもいない**。同じリポジトリに同居させると、絞り込んだ 4 機能に無関係な分岐を抱え込むだけになる。**復活させるときは別リポジトリで別立てにする。**

## 機能スコープ: 4 つに絞る

**「キャラのぶれ」を無くすための絞り込み**であって、単なる工数削減ではない。この 4 つ以外は当面やらない。

1. **曲紹介**
2. **朝挨拶**（特定の日は、前もって用意した原稿で上書きできる）
3. **チャットボット**
4. **11/4 バースデーライブ** → [birthday-live.md](birthday-live.md)

旧実装で Issue が立っていたが未実装だった機能（曲の管理、WebUI からの辞書更新、キーワード学習）は、上記に必要な範囲だけ作る。**機能を増やす提案をするときは「キャラの一貫性を損なわないか」を先に述べる。**

## 締め切り: 2026-11-01

11/4 が MAKOTO の誕生日（モデルの剣崎真琴と同じ）で、**11/1 から予告を始める**運用のため、機能的な締め切りは 11/4 ではなく **11/1（日）**。詳細と 2024 年の台本は [birthday-live.md](birthday-live.md)。

## 設計方針

### キャラの一貫性を第一の評価軸にする

旧実装は台詞コーパスを**そのまま返していた**とみられ、文脈を無視した投稿が実際に出ていた。これが「キャラのぶれ」の正体である可能性が高い。作り直しでは**コーパスを LLM の few-shot / RAG 素材として使う**方式に変える（詳細と実データは [makoto-legacy.md](makoto-legacy.md)）。

### SNS 本体を改造しない

モロヘイヤの設計方針をそのまま継承する。MAKOTO も **Mastodon 本体（フォーク含む）に手を入れずに、公開 API と webhook の外側で完結させる**。本体パッチが増えるほど upstream 追従の工数と衝突リスクが膨らむ。

### 管理操作は CLI で行う（WebUI の管理コンソールは作らない）

旧実装は `/makoto` に管理コンソールを持っていたが、**パスを知る利用者は運用者ひとりだった**うえ、退役後も nginx に残骸を残した（→ [makoto-legacy.md](makoto-legacy.md)）。makoto2 では管理コンソールを作らず、**原稿・辞書・曲データの更新といった運用操作はコマンドラインのサブコマンドとして実装する**。

- 認証・セッション・画面という付随物を持ち込まずに済む
- SSH 越しに実行でき、デプロイ・監視と同じ経路に乗る
- 旧実装で Issue が立っていた「WebUI からの辞書更新」も、**WebUI ではなく CLI として作る**

なお「WebUI」は利用者向けの機能を指す語としては引き続き使う（表記規約）。ここで作らないと決めたのは**運用者向けの管理コンソール**。

### コミュニティ・文化に資する

モロヘイヤと同じ北極星を共有する。MAKOTO は「サーバーを便利にするユーティリティ」ではなく、**コミュニティの文化そのものを増幅する存在**として設計する。増幅であって制度化ではない（参加は任意を死守する）。

### プロセスの寿命を設計に含める

旧実装は 2026-06 に**孤児プロセスが 11 日分たまり swap を 800MB 占有**し、同居していた本番サーバーの投稿レイテンシを劣化させた。停止・再起動・死活監視を後付けにせず最初から設計に含める。

⚠ **monit の `exec` は argv に分割されるため `&&` 以降が黙って捨てられる。** 本番 3 台の自動復旧がこれで長期間死んでいた実例がある。復旧コマンドはラッパースクリプトに逃がす。

## 情報の記載先ルール

- **課題・タスク** → GitHub Issue（`pooza/makoto2`）。**インフラ面の課題は `pooza/chubo2` の Issue として起票する**
- **プロジェクト共有すべき知見** → `docs/` 配下（git 管理下）に書く
- **インフラ情報** → `pooza/chubo2` の `docs/infra-note.md`
- **メモリを正本にしない** — 他端末・他セッションから読めないため、引き継ぎが必要な情報は必ず docs か chubo2 に書き、メモリには「どこに書いたか」のポインタだけ残す
- **クロスリポジトリの Issue 参照は `owner/repo#number` 形式**（`#123` だけでは同一リポジトリを指す）

## ブランチ戦略

| ブランチ | 目的 |
| --- | --- |
| `main` | リリース済み安定版。clone 時に得られるブランチ |
| `develop` | 開発ブランチ。日常の作業はここ |
| `feature/{issue}` | 大きな変更・並行作業が必要なときだけ切る（squash merge） |

### リリースフロー

1. `develop` で開発・コミット
2. リリース時に `develop` → `main` へ PR を作成しマージ
3. `main` でタグを打ちリリース

⚠ **`gh pr create` では `--base develop` を必ず指定する。** 省略するとリポジトリ default の `main` が base になり、未リリースの変更が黙って main に乗る（モロヘイヤで 3 件同時に踏んだ事故がある）。リリース PR のときだけ `--base main`。作成直後に `gh pr view <番号> --json baseRefName` で確認する。

## Issue / マイルストーン運用

- **Issue 駆動**。思いつきの改善は直接コミットせず、まず Issue 化する
- **「相談」と切り出された依頼は、選択肢の検討 → Issue 起票がゴール**。実装着手は明示の合図を待つ
- **スコープ確定 = GitHub マイルストーンの作成と割り当て**。docs にバージョン節を書くだけでは確定ではない

  ```bash
  gh api repos/pooza/makoto2/milestones -f title='0.2.0' -f state='open' -f description='...'
  gh issue edit <n> --milestone '0.2.0'
  ```

- **サイズラベルと重み予算**で管理する（件数では実態を反映しないため）

  | ラベル | 想定差分 | 重み |
  | --- | --- | --- |
  | `size:S` | 50 行未満 / 単発修正・docs | 1 |
  | `size:M` | 50〜200 行 / 新メソッド・契約変更 | 3 |
  | `size:L` | 200 行超 / 新機能・スキーマ変更・複数ファイル横断 | 8 |

  1 マイルストーンの目安は **20〜25 重み**。超えそうな Issue は次のバージョンへ送る。計画書は作らず、Issue ＋ マイルストーン ＋ 重み合計で管理する
- **新しいマイルストーンに着手したら最初にバージョンをバンプする**（開発中バージョンを常に識別可能にする。実行中のコードが判別できないとデプロイ・検証で事故る）
- **元要件を先送りするときは、受け皿の後続 Issue を起票するまで元 Issue をクローズしない**。「クローズ後に別途起票する」は消えるので、起票はクローズ前に行う
- **マイルストーン未設定の軽い課題は近接処理する**（重い作業の合間に片付ける）。ただし大きな設計案件はその場の雑談処理に混ぜない
- **ラップアップ時は、着地した Issue を「単純なモンキーテストができるか」で分類する** — 不可（内部最適化・純粋リファクタ）は即クローズ、可能なものは open 維持で軽いテスト観点メモだけ付ける

## リリース運用

### バージョニング

- パッチリリースは致命的な不具合時のみ
- 通常の機能追加・改善はマイナーバージョンでまとめる

### 通常リリース手順

1. マイルストーンの Issue をすべて消化
2. **リリース前レビュー**（下記）。赤のみ本リリースで対応し、黄・緑は Issue 起票して次へ送る
3. セキュリティレビュー（依存の脆弱性スキャン、Dependabot アラート確認）
4. **ステージング検証（省略不可）** — 専用 CT (`bydo`) にデプロイし、投稿・応答・スケジューラの動作を目視確認する。モロヘイヤでは検証を省略したリリースが本番障害（起動クラッシュ・ネイティブ拡張欠け）を出した実績があるため、緊急ホットフィックス以外で省略しない
5. バージョンバンプ（着手時に前倒し済みなら確認のみ）
6. リリース PR 作成（`develop` → `main`、`--base main`）
7. CI 緑を確認してマージ（コードが同一でも CI 結果を踏む）
8. タグ・リリースノート作成
9. デプロイ（プロセス停止 → 更新 → 起動、監視の停止／再開を挟む）
10. **リリース後の更新を漏らさない** — ① `docs/CLAUDE.md`（「開発中」→「リリース済み」、次バージョン節）② 公開ドキュメント（README / Wiki を作ったらそこも）③ `pooza/chubo2` の `docs/infra-history.md` にデプロイ記録 ④ メモリの同期

### リリース前レビュー

**単一のセキュリティレビューだけでは実用上の問題が取りこぼされる**（モロヘイヤ・capsicum の両方で実証済み）。以下 5 観点を独立に走らせて指摘を合流させる。

| 観点 | 焦点 |
| --- | --- |
| セキュリティ | トークン・API キーの取り扱い、シークレットの scrub、入力検証、SSRF |
| 外部 API 契約 | Mastodon API、iTunes Search API、LLM プロバイダの契約整合とレート制限 |
| 並行性・ライフサイクル | 常駐プロセス、スケジューラ、DB / キャッシュ接続、再接続、孤児プロセス |
| エラー処理・観測性 | 例外の分類、ログの個人情報漏洩、死活監視、失敗時の再通知 |
| コーディングスタイル・規約整合性 | lint、命名、表記規約（下記） |

指摘は **赤（必修＝データ破損・セキュリティ・ユーザー可視の機能不全）/ 黄（余力があれば＝単一 edge case・観測性ギャップ）/ 緑（送り＝将来の構造改善）** に分類し、赤だけ本リリースで対応する。

**機能が全台 OFF ＝ ライブ露出ゼロなら、真の赤でも非ブロック化して受け皿 Issue に繰越してよい**（モロヘイヤの Spotify OAuth で適用した判断）。

## コーディング規約

### Ruby（RuboCop）

モロヘイヤ・tomato-shrieker と同じ方針を引き継ぐ。

- **`Layout/EndAlignment: EnforcedStyleAlignWith: variable`** — 見栄えのための位置揃えを自動検出する（下記のインデント方針）
- **`Style/RedundantReturn: Enabled: false`** — 暗黙の return を使わない方針と衝突するため無効化する
- 収集スクリプト（[seed/](../seed/)）は Python のまま残してよい。RuboCop の対象外

言語に依存しない規約:

- **インデントは常に論理的な 2 スペース。** 見栄えのための位置揃え（代入の右辺に制御式を置いて深くインデントする等）は使わない。インデントの深さはコードの論理構造だけを反映する
- **暗黙の return を使わない**（Ruby を選ぶ場合、メソッド末尾でも `return` を省略しない）
- **lint / test を「環境が壊れている」で迂回しない。** 依存導入・環境修復をしてから必ず実行する。「CI が見るから」でローカル実行を省略しない
- **機能追加・バグ修正には対応するテストを書く**（CI で実行可能な範囲で。外部 API 依存のテストは無理に書かなくてよい）
- **fail-open な `rescue` の内側で設定値を読まない。** 設定パスの typo が例外として飲まれ、ガードが恒常 no-op になる（モロヘイヤで実際に踏んだ「守っているつもりで無防備」という静かな穴）。ガードのパラメータは定数化するか rescue の外で評価し、**「実際にブロックする」正テストを必ず書く**
- **秘密情報はログに出さない。** OAuth 認可コード・アクセストークン・API キーは scrub 対象に入れる

### ドキュメント表記規約

- **設定ファイルのパス**: ディレクトリを含めて表記する（`local.yaml` ではなく `config/local.yaml`）
- **サーバーの呼称**: 「インスタンス」ではなく「サーバー」
- **UI の呼称**: 「UI」ではなく「WebUI」
- **IP の表記**: 単独で使わず「IP アドレス」
- **ボットの呼称**: 英名ではなく日本語の役割名を使う
- **ファイル参照**: サンプルファイルやテンプレートへの参照はマークダウンリンクにする

## セッション開始時の同期手順

会話の最初に「進捗を同期してください」等の指示があった場合に実行する。

1. **このファイルを読む**（`MEMORY.md` は自動ロードされるので両者の整合性を意識する）
2. **リモートとの同期** — `git fetch origin` を**最初に必ず実行**（リモートが正本。ローカルを信用しない）→ `git log HEAD..origin/develop --oneline` → `git log --oneline -10`
3. `gh issue list --state open` / `gh pr list --state open`
4. **Dependabot セキュリティアラート** — `gh api repos/pooza/makoto2/dependabot/alerts`
5. **Codex レビューコメント** — 最近マージされた PR の `chatgpt-codex-connector[bot]` コメントを確認し、①未返信 → 対応判断して返信＋リアクション ②返信済みリアクション未付与 → `+1` を付ける ③両方済み → 完了。**返信とリアクションの両方揃って「完了」**
6. **Sentry**（導入したら）— `sentry-cli issues list` で未解決を確認し、判断をコメントに記録
7. **`pooza/chubo2` の同期確認** — `git fetch origin` + `docs/infra-note.md` の変更、open Issue の変動。あわせて **MAKOTO に関係する chubo2 Issue**（実行環境の CT、cure-api の公開露出、モロヘイヤの webhook 経路など）を拾い、makoto2 側の作業の前提になっていないか確認する
8. **マイルストーンの状態確認** — docs / メモリの記載と GitHub の open/closed が一致しているか
9. メモリの更新 → 結果を報告

## デプロイ・運用

- **デプロイは SSH 経由。ステージング → 本番の順**
- リモートの `develop` が diverge したら、merge-only を確認したうえで `reset --hard` で origin に揃えてよい
- 稼働先の構成・SSH エイリアス・接続情報・チューニングは [pooza/chubo2 インフラノート](https://github.com/pooza/chubo2/blob/main/docs/infra-note.md) を正本とする

⚠ **このリポジトリは public。** ネットワーク構成（許可 CIDR・プレフィクス）、ホストの権限設定、バックアップの所在といった運用の詳細は**このリポジトリに書かず、chubo2（private）側に書く**。docs には「chubo2 を見よ」というポインタだけを置く。

### 実行環境: 開発は `bydo`、本番の置き場は未決

**開発用の専用 CT `bydo` が 2026-07-30 に用意された**（Proxmox `pve` 上の LXC・Ubuntu 26.04・2 vCPU・2GB）。node 定義（rbenv ＋ Ruby 4.0.6）はコミット済みだが、**レシピは未適用（未着工）**。アドレス・接続情報は [pooza/chubo2 インフラノート](https://github.com/pooza/chubo2/blob/main/docs/infra-note.md) を見る。

- **`bydo` は開発環境であって、ステージングでも本番でもない。** リリース手順の「ステージング検証」も当面はこの CT で行う（本番が決まるまでは開発環境と検証環境が同じであることを承知の上で運用する）
- **本番の置き場は未決** — Linode か、pve 内にもう 1 CT か。`pooza/chubo2#98` で追う。締め切り（11/1）から逆算すると、**10 月中に検証を終えるために遅くとも 9 月中には決めて建てる必要がある**
- MAKOTO 本体を動かす前提（Ruby 4.0.6・常駐 1 本・SQLite）は既に確定済みなので、CT 側に足りないのは**レシピの適用と死活監視**（→ #15、`pooza/chubo2#98`）

### 引き継いだ既知ドリフト

nginx の `/makoto` ロケーションが Mastodon フォークの vhost に残っており、**キュアスタ！のサーバー移行（gomander）にもそのまま引き継がれている**。バックエンドの 3011 は誰も listen していないので実害は 502 のみ。**これは旧実装の管理コンソールで、makoto2 では踏襲せず削除する**（`pooza/chubo2#99`）。詳細は [makoto-legacy.md](makoto-legacy.md)。

## スタック（2026-07-30 決定・#2）

**Ruby ＋ `ginseng-*` 系 gem。常駐プロセス 1 本 ＋ プロセス内スケジューラ。**

コードは旧実装から引き継がないが、**フレームワークは引き継ぐ**。この 2 つは矛盾しない。

| 選んだもの | 理由 |
| --- | --- |
| Ruby | モロヘイヤ・tomato-shrieker と同じ系譜。chubo の rbenv / ruby cookbook をそのまま流用でき、ステージングには Ruby 4.0.6 が既に入っている |
| `ginseng-core` | `daemon.rb`（pid 管理・start/stop）・`command_line.rb`・`logger.rb`・`config.rb` が既にある。**「プロセスの寿命を設計に含める」「管理操作は CLI」をゼロから書かずに済む** |
| `ginseng-fediverse` | `mastodon_service.rb` があり、投稿疎通（#7）がほぼ消える |
| 常駐 1 本 ＋ 内蔵スケジューラ | Redis 不要で 2GB CT に収まる。監視対象が 1 プロセスなので死活監視も単純 |

### 却下した選択肢

- **Sidekiq + Redis（旧実装・モロヘイヤ踏襲）** — モロヘイヤは webhook を大量に捌くので必要だが、MAKOTO の負荷は平常時 5〜7 投稿/日 ＋ ライブ当日 8 時間で桁が違う。**2GB CT に重く、孤児プロセスを撒いた構成そのもの**
- **Python** — [seed/](../seed/) の収集スクリプトが Python で LLM の SDK も充実するが、主戦場ではなく chubo のレシピも Ruby 寄り。ginseng 相当を全部書くコストが 94 日に直撃する
- **素の Ruby（ginseng を使わない）** — 依存は減るが daemon 管理・設定・ログ・Mastodon クライアントを自前で用意することになる

### ⚠ 再考の引き金

**Ruby の弱点はベクトル検索・埋め込みなど ML 寄りのエコシステムに限られる。** 台詞 561 件はプロンプト同梱で足りる前提なので現状は表に出ないが、**#3（LLM プロバイダ）や #4（データストア）でベクトル検索を伴う RAG を選ぶなら、この決定を見直す**。

なお **[seed/](../seed/) の収集スクリプトは Python のまま運用ツールとして残してよい**（#9）。ボット本体と同じ言語である必要はない。

## LLM プロバイダとモデル（2026-07-30 決定・#3）

**Anthropic Claude / `claude-opus-5`。全機能で同じモデルを使う。**

- **公式の Ruby SDK がある**（`gem install anthropic` → `Anthropic::Client.new`）。Messages API・ストリーミング・プロンプトキャッシュ・ツール呼び出しが揃っており、「LLM だから Python」はクライアント層では成り立たない
- **機能ごとにモデルを変えない。** キャラの一貫性が第一の評価軸である以上、語り口の基準を 2 つ持つのは目的に逆行する。コスト最適化は必要になってから

### コーパスはプロンプトに全部載る（実測）

**応答に使える台詞 561 件で 6,969 文字**（平均 12 文字・最長 70 文字）。`quote` 956 件と `message` 388 件を合わせても 3 万文字弱で、**コーパス全体がシステムプロンプトに収まる**。

⚠ **ベクトル検索も RAG 基盤も要らない。** これで「Ruby の再考の引き金」は実質消えた（→ 上記スタックの節）。

### 実装上の要点

- **プロンプトキャッシュを使う。** コーパスをシステムプロンプトの先頭に固定し、末尾のブロックに `cache_control` を置く。ライブ当日は 2〜3 分間隔で投稿するので **1 時間 TTL** が効く（8 時間 194 曲で概算 $10 → $3）
- ⚠ **Ruby SDK は `system_:`（末尾アンダースコア）** — `Kernel#system` との衝突を避けるため。`system:` ではない
- ⚠ **レスポンスの `.type` は Symbol**（`:text` であって `"text"` ではない）
- ⚠ **`stop_reason` が `:refusal` のことがある。`content` を読む前に必ず分岐する。** 安全性の分類器が働くと HTTP 200 で本文が空になるので、`content[0]` を無条件に読むコードは壊れる。**MAKOTO は無人で投稿し続けるので、拒否されたら定型文にフォールバックして黙って落ちないようにする**
- サーバー側フォールバック（`fallbacks: "default"`）を既定で有効にする
- **API キーは `config/local.yaml`（gitignore）に置き、ログの scrub 対象に入れる**

### ⚠ Claude Max の契約枠では API は使えない

**Max プランは claude.ai / Claude Code / デスクトップアプリ向けで、API 利用は含まれない。** MAKOTO が API を叩く分は Developer Platform 側の従量課金になる（別勘定）。「Max が余っているからその枠で」は成立しないので、API クレジットを別に用意する。

そのうえで、**実行時に LLM を呼ぶ範囲を絞れば従量課金はかなり小さくできる**。

| 機能 | 実行時に LLM を呼ぶか |
| --- | --- |
| 朝挨拶 | **原則ノー。** 前もって用意した原稿を配信する（#12 の上書き機構）。素材は `morning` 237 件 |
| バースデーライブの告知・進行 | **ノー。** 台本は前もって書く。11/1 の予告も同じ |
| 曲紹介 | 紹介文テンプレート ＋ 曲データで足りるなら不要。語り口に幅が欲しいところだけ呼ぶ |
| チャットボット | **イエス。** ここだけは実行時に必要 |

原稿・台本の執筆そのものは **Max の枠内で対話的にやればよい**（Claude Code や claude.ai で書いて `message` に流し込む）。**API 課金が必要なのは実質チャットボットだけ**になる。

### 予算の目安は月 $10（利用状況で見直す）

原稿方式に寄せた結果、**定時投稿の課金はほぼゼロになり、この枠はまるごとチャットボットに使える**。ハードリミットではなく、**運用しながら見直す前提の目安**。

前提: システムプロンプトに台詞 561 件を同梱すると概算 12,000 トークン。Opus 5 は入力 $5 / 出力 $25 per MTok。

| 条件 | 1 応答あたり | 月 $10 で |
| --- | --- | --- |
| キャッシュ無し・561 件同梱 | 約 $0.065 | 約 150 回（1 日 5 回） |
| キャッシュ読み・561 件同梱 | 約 $0.011 | 約 900 回（1 日 30 回） |
| キャッシュ無し・150 件に絞る | 約 $0.020 | 約 500 回（1 日 16 回） |

⚠ **プロンプトキャッシュはチャットボットではライブほど効かない。** メンションが散発的だと 5 分 TTL が切れ、毎回キャッシュ書き込み（1.25 倍）が乗って**かえって高くつく**。効くのは会話がバースト的に来るときだけで、定時投稿とは前提が違う。

**歯止めは 3 つ用意する。**

1. **同梱する台詞を絞る** — 効果が一番大きい。`form` と `priority`（1〜5 に分布）で選抜する。**何件同梱すれば語り口が保てるかは #19 で実測して決める**
2. **1 日あたりの応答回数に上限を持つ**（コード側・#18）
3. **Console 側に支出上限を設定する**（運用側）

### LLM が落ちてもライブは走る

**8 時間の枠は LLM の可用性に依存させない。** 生成に失敗したら台詞コーパスから定型で投げるフォールバックを最初から用意する（→ #10 / #13）。

## データストア（2026-07-30 決定・#4）

**SQLite ＋ Sequel。**

旧実装は PostgreSQL で `ginseng-postgres`（pg + Sequel）も手元にあるが、**保持するデータが小さく、常駐プロセスを増やしたくない**ため採らない。

| データ | 量 | 性質 |
| --- | --- | --- |
| 台詞コーパス | 1,340 行 | 更新は稀・読み取り専用に近い |
| 曲 | 4,305 行 | 同上 |
| 投稿履歴 | 増え続ける | 重複回避のための書き込み |

- **常駐プロセス 1 本という決定と整合する。** PostgreSQL を建てると監視対象と「ライブ 8 時間の間に落ち得るもの」がもう 1 つ増える
- **Sequel を挟むので、後から PostgreSQL へ移せる**（`ginseng-postgres` も Sequel ベース）
- 2GB CT に対して圧倒的に軽い

### ⚠ バックアップは `VACUUM INTO` で取る

**稼働中の SQLite ファイルを生でコピーすると壊れた写しになる。** `writersbase-tools` の `google_drive_backup` は `rclone sync` でパスを生コピーするため、そのままでは使えない（chubo2 が Uptime Kuma で同じ判断をしている）。**`VACUUM INTO` で一貫スナップショットを作ってから上げる。**

コーパスは唯一の代替不能な資産なので、バックアップ手順は #8 の完了条件に含める。
